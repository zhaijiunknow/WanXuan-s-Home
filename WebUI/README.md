# WebUI · VN 前端原型

用 HTML/CSS 做的界面。放在 `Assets` 之外，Unity 不会导入它。

## 目录结构：三套界面，两套页面

**主菜单和游戏界面是两个场景，因此也是两套互不加载的页面。**
**第三套（Animus 归档系统）两边都要用，所以它是一份共用代码。**

```
WebUI/
├── bridge.js        共用：与 C# 的协议层（信封 / 版本号 / 四种发送方式 / __vnReceive 分发）
├── stage.js         共用：1920x1080 画布等比缩放
├── theme.css        共用：三套主题变量 + 页面基础 + #stage
│
├── index.html       ← 游戏界面（MainRoom 场景加载这个）
├── style.css            只含游戏规则
├── app.js               只含游戏逻辑
├── story.js             剧本数据（Unity 菜单导出，见下）
├── story.sample.js      内置样本
├── uwbtest.html         诊断页（不是游戏的一部分）
│
├── animus/          ← Animus 归档系统 = 设置页 + 暂停菜单（**两个页面共用**）
│   ├── animus.css           视觉语言：客厅的四种光 / 网格 / 扫描线 / 档案盘（四套主题）
│   ├── animus.js            外壳：生成 DOM、索引绳导航、切页、Esc / ↑↓
│   ├── settings-module.js   设置内容（一张数据表 → 四个子页）
│   └── memory-module.js     记忆序列（剧情进度树）
│
└── menu/
    ├── index.html   ← 主菜单界面（MainMenu 场景加载这个）
    ├── background.css   只有动态背景的底色/网格/光/暗角
    ├── background.js    只有动态背景的画布内容（索引绳 + 线索链 + 尘埃）
    ├── menu.css         只含主菜单规则
    ├── menu-view.js     只含主菜单逻辑
    └── boot.js          唯一同时认识"主菜单"和"Animus"、也唯一认识 C# 的地方
```

**共用的有四样：协议层、画布缩放、主题变量、Animus。** 它们不是"某一页的界面代码"，
重复实现会立刻漂移（协议版本号分成两份 → "设置页能存、游戏页读不到"这种极难查的 bug）。

主菜单和游戏的**界面**代码一律不共用：它们永远不同屏（是两个场景）。
但 Animus 不同 —— 它是同一个系统出现在两处，复制两份必然出现"主菜单里能关立绘、
暂停菜单里关不掉"这类不一致。

> 游戏页在根目录而主菜单在 `menu/` 下，看着不对称 —— 这是刻意的。`MainRoom.unity` 里的
> WebView 地址指向 `WebUI/index.html`，保持它不动就少动一次场景文件（手写场景 YAML 是
> 这个项目里风险最高的操作）。文件名里的 `index` = 游戏，`menu/` = 主菜单。

## 立刻看效果

两个界面都可以**直接用浏览器打开**，不需要 Unity、不需要起服务器：

- **游戏界面**：双击 `index.html`。会加载 `story.js` —— **完整 1397 步**就在里面；只有这个文件不在时才退回内置样本（真实剧本第一幕的摘录 + 真实选项与两个结局）。
- **主菜单界面**：双击 `menu/index.html`。打开的就是 **Animus 桌面本身**（桌面 = 主菜单，见下），
  进「设置 → 声音」能拖滑杆，但"开始游戏 / 退出"需要 Unity 才能生效。
  它的「章节选择」直接引 `../story.js`，所以 25 章在浏览器里就能看全（立绘要 `WebUiServer`，见下）。

`WebUI/story.js` 是**已经导出好的**（1397 步，文件头 `exportedAt` 写的是 `2026-10-01 16:01:03`），不用先跑一遍菜单才能看到完整剧本。剧本改了之后要重新生成它：先执行 Unity 菜单 `WanXuan > Import Long Story`，再执行 `WanXuan > 导出 Web 剧本（story.js）`。

加载优先级（`app.js` 里 `loadStory()`）：

1. **`story.js`** —— `<script>` 加载**不受 `file://` 的 CORS 限制**，所以嵌进 CEF / WebView 时只有这一条能成。这是主格式。
2. `story.json` —— 旧的 JSON 格式，用本地 http 服务打开时可用（`python -m http.server 8000` 之类）。
3. 内置样本 —— 保证任何情况下打开都有东西可看。

> 为什么主格式从 `story.json` 改成 `story.js`：CEF 里 `fetch('story.json')` 会被 CORS 拒绝，导致 WebView 里永远只能跑样本。而 `<script src="story.js">` 没这个限制，代价只是文件头多一行 `window.VN_STORY = `。

## 操作

| 操作 | 键 / 按钮 | 在哪一页 |
|---|---|---|
| 推进对话 | 点击、`空格`、`回车` | 游戏 |
| 打字中点击 | 立刻显示完整文字（VN 惯例） | 游戏 |
| 选择选项 | 点击，或按 `A`–`C`（按钮右边显示的就是这个键位；也兼容 `1`–`9`） | 游戏 |
| 自动播放 | `A` | 游戏 |
| 快进（文字瞬间显示） | `F` | 游戏 |
| 隐藏 UI | `H`（隐藏后点任意处恢复） | 游戏 |
| 切换主题 | `T`（木牌 / 暖棕 / 奶油） | 游戏 |
| 背景预览开关 | `B` | 游戏 |
| **参考层**开关（角色站位框 + 面部安全线） | `G` | 游戏 |
| 开发 HUD | `D` | 游戏 |
| **回主菜单** | `M` 或控制条上的「主菜单」 | 游戏 |
| **暂停菜单** | `Esc`（再按一次继续） | 游戏 |
| 开始游戏 / 设置 / 退出 | Animus 桌面上的瓦片（鼠标点或 `↑` `↓` + `回车`） | 主菜单 |
| 上下选择 | `↑` `↓`，`回车` 确认 | 两处 |
| 关掉 Animus | 暂停菜单：`Esc`（= 继续游戏）；主菜单：**没有关掉这回事**，要退出得选桌面上的「退出游戏」 | 两处 |
| 从设置里退出来 | 底栏「返回」或 `Esc` —— **两条路都要能用** | 两处 |

控制条（游戏页左下）有同样的按钮。

> **右下角那行提示跟着状态走**（`app.js` 的 `setHint()`）：
> 对话「点击 / 空格 继续」、选项「点击选择 · 或按 A / B」、结局「按 Esc 先收起这张卡」。
> 它原来是一条写死的字符串，于是选项页和结局页上都在说"点击继续" ——
> 而那两个状态下点击**是不推进的**（`advance()` 见到选项层/结局层直接返回）。
> **屏幕上不该写一件按不出的事。**
>
> 同一件事的另一半：`showToast()` 借用同一行显示临时消息，2.2 秒后必须回到
> **当前这一档**的提示（`state.hint`），不能写死回"点击 / 空格 继续" —— 否则
> 在选项页上按一下 `A`（自动播放）就会把提示又变回那句做不到的话。

> 游戏页的 `M` 和「主菜单」按钮**不是"切出菜单界面"** —— 它只是请求 C# 换到 MainMenu 场景。
> 想留在游戏里调设置就按 `Esc`，那是暂停菜单（Animus），和换场景是两件事。

**Animus 里的操作**：`↑↓` 在档案盘之间切换子页，`Esc` 收起来。暂停菜单里
`Esc` / 「继续游戏」都是"继续"，底栏另有「回主菜单」和「退出游戏」。
主菜单页**不一样**：那两格（开始游戏 / 退出游戏）是桌面上的瓦片，`Esc` 收不掉它
（见下面「Animus 桌面就是主菜单」那一节）。

`B` 和 `G` 是**两个独立开关**：`B` 控制 CSS 假房间，`G` 控制那两条参考标线。想拍干净的设计稿就按 `G` 关掉参考层，不必连背景一起关。

**拍截图时请先按 `D` 把 HUD 打开**——HUD 里会显示当前主题名和字体加载状态，这样一张图就能说清是哪个主题，不用猜。

## 三个值得先看的点

1. **按 `B` 关掉背景预览**：整页会变透明。这就是接进 Unity 后的真实状态——Live2D 角色和房间从 HTML 底下透上来。**这一步能验证对话框的对比度在真实条件下是否够用。**
2. **按 `T` 切主题**（三套，可来回对比）：
   - **`room`（默认，木牌 / 贴纸）** —— 从 `MainRoom` 实拍取色衍生。不透明奶油纸面 + 暖褐木色边框 + 下缘加厚做出"木牌厚度" + 硬阴影，青绿作强调色。**不用毛玻璃。**
   - `cocoa` 暖棕深色 —— 通用安全牌，磨砂玻璃语汇。
   - `cream` 奶油浅色 —— 磨砂玻璃语汇。注意它的面板色接近你的墙面，分离度不足，留作反面对比。
3. **按 `D` 开 HUD**：能看到当前 `stepId`、进度、`background`、表情标注，以及 `【场景】/【BGM】/【立绘】` 这些**演出提示**。这些数据在 Unity 的 `StoryStep.StageNote` / `MarkerTitle` 里已经存在但从来没被用过，这里先把它显示出来。

## room 主题的取色依据

不是凭感觉配的，全部来自 `MainRoom` 实拍：

| 场景元素 | 色值 | 用在哪里 |
|---|---|---|
| 墙面奶油 | `#EFE6D6` | 面板底色基调（面板取略亮略净的 `#FDF8EF`） |
| 墙裙 / 家具木色 | `#8A6247` `#6E4C36` | 面板与选项边框、名牌、木牌下缘 |
| 地毯 / 窗框 / 坐垫青绿 | `#3E8C84` | 强调色：角标、继续指示器、选项悬停条、幕标题分隔线 |
| 角色光环金 | `#E8C56A` | 只在结局卡的装饰符上出现一次 |
| 草莓粉 | `#C9606F` | **只留给结局卡的分隔线** |

两条刻意的取舍：

1. **不用毛玻璃。** 你的低多边形场景里没有任何半透明模糊材质，全是平涂 + 清晰描边 + 硬阴影。磨砂面板压上去会立刻显得"这是另一个软件的画面"。
2. **面板做成不透明。** 对话框落在芥黄地板 + 青绿地毯描边上，底部区域很花；不透明才能保证文字对比度是**确定的**，而不是碰运气。想让它透一点，把 `--panel-bg` 的色值改成 `rgba(...,0.94)` 即可 —— 边框和阴影仍然负责把面板和墙分开。

变量在 `style.css` 顶部拆成了**配色组**和**结构组**。改色只动配色组（`--panel-bg` / `--text-main` / `--accent`…），不要动结构组（`--panel-backdrop` / `--panel-radius` / `--panel-border-bottom-w`…）。

## 构图：角色是居中偏右的

按实拍确定，不是想当然：

- 角色占据画面中间约 38% 宽，**泡泡袖张开后视觉宽度接近 980px**；
- 头顶光环约在画面 **29%** 高度，眼睛约在 **49%** 高度，身体一直到画面下沿被裁掉。

所以 `#character-slot` 已改成**居中**（之前错放在左侧），并加了一条红色的**面部安全区标线**（距下沿 546px）：对话框上沿不应越过它。

对话框当前是 `bottom: 62px` + `min-height: 250px`，上沿在 312px，离安全线还有余量。但**中文长句到 6 行左右时上沿会到约 558px，就会切到她的脸** —— 这条线就是给你盯这个用的。

另一个已知冲突：**选项按钮（880px 居中）弹出时会几乎完全盖住她**，而选项恰恰是情绪最高点。两个改法，等你定：

- 选项改成左对齐竖列，把她留在右侧可见区；
- 或者利用你有 3D 相机这一点，选项时把镜头平移，让她挪到右侧三分之一。

## 中文字体：你看到的很可能不是游戏字体

`style.css` 里 `@font-face` 指向 `../Assets/.../ChillRoundF.ttf`。但 **`file://` 下浏览器通常以 CORS 拒绝加载跨目录的字体文件**，于是静默退回系统字体（微软雅黑之类）。字体文件本身不报错、画面也正常，所以极容易在"以为在看游戏字体"的情况下评排版。

所以 `app.js` 会主动检测并把它显示在 HUD 上：

```
字体    : ChillRoundF 已加载
字体    : 未加载 → 正在用系统字体（评排版时务必注意）
```

如果显示未加载，两种解法：

1. 在 `WebUI` 目录起静态服务后访问 `http://localhost:8000` —— 相对路径即可生效；
2. 把 `ChillRoundF.ttf` 复制到 `WebUI/fonts/`，并把 `@font-face` 的 `src` 改成 `url("fonts/ChillRoundF.ttf")`。

> 顺带一提：这个字体是**寒蝉系圆体**，授权条款和文泉驿不同，商用前请确认。

## 两个还没定的技术前提（会影响最终配色）

**1. UI 走不走后处理？** URP 里这决定了颜色会不会被改：

| UI 挂载方式 | 是否被后处理影响 |
|---|---|
| **Screen Space - Overlay** Canvas | **不受影响**（后处理之后才画到 backbuffer） |
| Screen Space - Camera / World Space Canvas | **受影响**（Bloom / Tonemapping / Color Grading / Vignette 全作用） |
| 原生 WebView 窗口叠加 | 完全在 Unity 之外，不受影响 |

三个后果：

- 如果打算"统一后处理"，**不要照当前未调色的截图去定 UI 颜色** —— 整幅画面会一起漂移，调好的值全部作废。
- **Bloom 对亮面板是灾难**：面板接近纯白会发光、文字边缘发糊。你的场景是高明度低对比的，这个风险是实打实的。
- **Vignette 会先压暗 UI 四角**，角标和按钮会变脏。

建议：**UI 走 Screen Space - Overlay（不进后处理），"统一"只作用于 3D 场景**，让文字可读性可控。若最终一定要 UI 也被调色，请按调色**之后**的目标反推颜色。

**2. 目标宽高比。** 参考截图是 999×810（约 1.23:1），不是 16:9。当前舞台按 1920×1080 写死：如果是截图裁切则无需改动；如果 Game 视图就是这个比例，所有布局参数都要按新比例重算 —— 告诉我一声即可。

## 两个场景与流转

| 场景 | 加载的页面 | 里面有什么 |
|---|---|---|
| **`Assets/Scenes/MainMenu.unity`** | `WebUI/menu/index.html` | 只放一个 UWB 预制体 + EventSystem + 相机。没有 GameManager、没有 StoryManager、没有 Live2D —— 主菜单不需要剧情引擎 |
| **`Assets/Scenes/MainRoom.unity`** | `WebUI/index.html` | 完整的游戏场景（房间 / Live2D / 剧情引擎 / 游戏 UI） |

两个场景都必须出现在 **File > Build Profiles（或 Build Settings）** 里，否则换场景会失败。
`WebSceneFlow` 会先检查再载入，载入不了会打一条能直接照做的报错，而不是抛异常。

```
MainMenu ──menu.start──► MainRoom
MainRoom ──ui.menu─────► MainMenu
```

流转由一个自动挂载的组件负责（`Assets/Scripts/UI/WebSceneFlow.cs`）。**它在哪个场景都一样工作**，
所以两个场景都不需要手写脚本 GUID 引用 —— 这一点很重要，见下面"为什么不用场景配置"。

### 进游戏的那一下：**在静止的光里切换，动态全部留给新场景**

**这一下要跨三个边界**：网页这一层、Unity 的场景、还有一次整页跳转。
中间那段时间（C# 换场景 + 新页面加载，**1~3 秒**）无论怎么排都会露出硬切，
区别只在"怎么处理这段"。

参考是《失落星船：马拉松》进图那一下（配装页 → 地图页 → 进图）：

- 它的整个切换发生在画面**静止**的时候 —— 玩家看不到"换场景"这件事；
- 切过去之后，画面是**一块一块揭开**的（散射顺序，不是从左往右扫），
  底下先是一张**轻微马赛克**的画面；
- 然后整体**一起变清晰**，最后才把 UI 显示出来。

关键在于：**那段等待不是被藏起来了，而是被拿来当演出**；
而且**切换放在静止里，动态全部由新场景提供**。

```
0–190ms     她扑向镜头（放大 1.35、亮度顶起来）+ 归档界面被撞开（缩小、左退、抖、故障撕裂）
190–370ms   她的光炸开、盖满整屏 —— 这片光是**当前主题**的色
370–520ms   光保持住（静止）
520ms       网页才发 menu.start —— **C# 就在这片静止的光里换场景**
            ↓ Unity 侧 ChapterTransition 盖上的第一帧就已经是"主题色**被切成大小不一的块**"
              （二分空间切分。**底色块都是同一个颜色** —— 切分不是为了好看，
                是为了消失时能"对位"：色块走的时候，它底下那块底色跟着走）
2.2s        **一块接一块地出现**（从屏幕中心向外、带抖动），每块颜色取自 Unity 场景对应位置
            ↓ 出现的是"场景块"，散乱地浮在底色块上，允许叠加、允许留缝
等 ready    停在这儿 —— 这就是"还在装载"的样子：真的在等网页
0.75s       **底色块与场景块共用一套排队**，整个画面一块块退 → 露出真正的 Unity 场景
```

- **静止帧是"当前主题的光"，不是黑、也不是抓屏**：
  - 黑：不在这套界面的配色里（四套主题最深的"夜"也不是黑），读起来是"信号断了"；
  - 抓屏：换场景那一帧屏幕已经在换，抓不到旧页面最后那一眼；要在切换**之前**抓，
    就得再引入一次握手；
  - 主题的光：网页退场本来就停在 `#handoff-veil` 上，而那条规则现在是
    **主题色渐变**（`theme.css` 用 `--ax-bg-lift/mid/deep`，四套主题各一份）。
    Unity 用同样三个色值、同样 158°/38% 烘了一张渐变 —— 两边逐字一致，
    所以"静止帧"和网页最后一眼是同一片光，**接上去看不出接缝**，
    而且"根据主题来"是自动成立的：午后是落地窗那片白，雨夜是窗子那片冷光。
- **主题得由网页报过来**：主题模式有 `fixed / time / story` 三种，实际生效的那套是
  网页算的（`renderedTheme()`），不一定是设置里存的那个。所以
  `settings-module.js` 每次切主题都发一条 `ui.theme`，`ChapterTransition` 按它挑颜色，
  还没收到时退回 `UiSettingsStore.Current.animusTheme`。
  ⚠ **四套色值在两个地方各写了一份**（`animus.css` 的主题块 / `ChapterTransition.WashFor()`），
    改一边必须改另一边。`animus.css` 那四个块还挂了 `:root[data-theme=…]` 的别名 ——
    交接那层光在 `#animus` 外面，靠这份别名才读得到变量。
- **这一版的机制**（换场景之后那一段）：主题色铺底 → **从屏幕中心长出大小不一的色块**
  （每块颜色取自 Unity 场景对应位置）→ 铺满时停住等网页 `ready` → 色块渐隐、底色透明，
  露出真实场景。**"装载"就长在"铺满并停住等"这一步上**：整屏是一张用这个房间的
  真实颜色拼出来的静帧，它在等真的东西 —— 页面快就快、慢就慢。
  ⚠ 走过几版弯路，记在这儿：散射揭开的马赛克读起来是"特效"、光坠下去是"镜头在动"、
  扫描线是"系统界面压在上面"—— 都不如"这个房间自己长出来"。
- **每幕一条配方**（`ChapterTransition.cs` 顶部的 `Recipes` 表）：
  机制是**一套**（主题色铺底 → 从中心长出色块 → 铺满后等 `ready` → 化开），
  每幕换的是**参数**：色块数量、铺满多快、化掉多快、色块的明暗差异。
  表里已经写了 **1-1**：S01 寂静客厅是"午后的光安静地铺过地板"
  （`场景需求表_皖萱的家.txt` 的 S01 原话，`animus.css` 午后那套的注释也是这句），
  所以它**更慢**（2.2s）、色块**更少**（18 块）——
  换算下来每块 122ms 一次，其中 30ms 出现、约 90ms 停着。
  ⚠ **"每块停留久一点"要同时动两个数**：把配方的 `assembleSeconds` 拉长、
  把 `AppearPopSeconds` 压短。只拉长前者会变成"慢慢淡出来"，读不出"一块一块"。
  ⚠ **覆盖率是这一层的构图预算**：块数 × 单块面积 ⇒ 1-1 约占两成画面，
    剩下八成是主题色的底。**先看单块尺寸再看块数** —— 块只要大一点，
    两三块就能盖掉半个屏幕，"大部分是底色"就不成立了。
  其余幕暂时走最后那条**默认** —— 表没写完也不会坏。
  加一幕 ＝ 加一条数据。`Play(chapterKey, shortForm)` 是给"幕与幕之间"留的入口：
  场景切换那条路已经通了，幕内那条还没接（接的时候从发 `marker.show` 的地方调）。
- **色块为什么必须取场景的颜色**：它们是"这个房间自己一块块长出来"，
  取色是它成立的全部理由 —— 所以最后化开时几乎看不出接缝（色块本来就是场景的颜色）。
  取色用**一台临时相机渲进 96x54 的小 RT 再读回内存**，不是抓屏：
  那一刻屏幕上盖着这一层，抓屏抓回来就是自己；要在切换之前抓又得再引入一次握手。
  临时相机只手动 `Render()` 一次、只在内存里跑，屏幕上什么都看不见。
  ⚠ RT 用的是 sRGB（`RenderTextureReadWrite.sRGB`）：读回来的值要和 uGUI 用的颜色
    在同一个空间里，否则色块会偏暗偏灰。
- **色块怎么摆**：分两层。
  **底**是主题色**被切分**成 `BaseTileCount` 22 块（二分空间切分 → 大小不一但严丝合缝铺满），
  **每块都是同一个颜色**（主题的 `--ax-bg-mid`）。切分的唯一目的是消失时能"对位"。
  **上**面是散乱的**场景块**：随机矩形，大小不一（多数小、约五分之一 ×1.6）、
  位置散乱（允许出画一点）、**允许互相叠加、也允许留缝**。
  缝里露出的是**底色块**（那是这一层的一部分，不是漏了）；
  叠起来的地方后摆的压住先摆的，**消失时下面那块会露出来，所以读起来是一层层揭开**。
- **剧本要等过场演完才开始**（`GameManager.StartStoryAfterTransition`）：
  剧情一开跑就会往网页推 `story.load` / `dialogue.show`，那些内容在过场期间藏在色块底下 ——
  等色块退完，第一句可能已经播到一半了。所以要晚的是**剧本本身**，不是画面。
  判据是 `ChapterTransition.IsBusy`（协程最后、化开完并隐藏之后才置回 false）。
  ⚠ 这里必须用协程等，不能直接调：`StartStory` 会"取走并清空"一次性的续玩点，
    而过场要用同一个续玩点去推"这次进的是哪一幕"，得让它先读完。
  （握手 `hello` 不受影响，网页一 `ready` 就发 —— 不然会踩到网页那个 3 秒的 standalone 兜底。）
- **消失的时间是"对位 + 随机"的**（对位是把底色切分的全部理由）：
  场景块的消失在**一套洗过的顺序**上（Fisher–Yates 洗牌 + 一点抖动）—— 所以是零散地一块块没，
  不是从中心一圈圈退回去（出现那套"从中心向外、带抖动"没动，那一边看着是对的）。
  **每一块底色跟着压在它上面的那块场景块走**（取最早的那块）——
  色块一走，它底下那块底同时走，那个位置当场就是真实场景，不会留一块底色在那儿。
  没被任何场景块压到的底色块，也**随机**分散在化开的后 80% 里，所以同样是零散地走完。
  ⚠ 这里**没有整屏的底 quad** —— 底就是那些块本身，所以不存在
    "化开还没开始、底色先整片没了"。早先有过一个 quad，它正是那个毛病的来源，已删掉。
- **可调的数**：每条配方里是 `leafCount` / `assembleSeconds` / `dissolveSeconds` /
  `variation`（色块明暗差异，会在化开时衰减到 0，所以最后一块块都回到取色本身）；
  全局的是 `SampleWidth`/`SampleHeight` 96x54（取色精度）、`SampleGrid` 3（每块取 3x3 个点平均）。
- **收光的判据只有网页发来的 `ready`**，而且它必须是**画过一帧之后**才发
  （两页都放在嵌套两层的 `requestAnimationFrame` 里）。这条踩过两次，都记在这儿：
  1. 拿"引擎级就绪"（`ReadySignalReceived`）当判据 —— 那个信号只代表 CEF 进程起来了，
     网页那时**还没画第一帧**。揭开后玩家看到的是**没有 UI 的真实场景**，
     紧接着网页画出来、那层白色的 veil 才"啪"地出现 —— 观感是"先露馅，再闪一下白"。
  2. 只等**一个** `requestAnimationFrame` 就发 `ready` —— rAF 的回调跑在"这一帧即将被画出来"
     **之前**，所以那一刻画面其实还没上屏，同样会露馅。嵌两层才落到第一帧之后。
  兜底 4 秒（页面启动就抛异常时才会走到）。
- **盖着的时候挡住点击**（`CanvasGroup.blocksRaycasts` 只在揭示期间为真，结束就关）：
  这一层是全屏的，点击要是穿过去，玩家在光里点一下就是在操作底下的网页 ——
  表现是"看不见的那一句被跳过了"。
- **两边的方向必须相反**：UI **退**、她 **进**。方向一致只会读成"整页放大"，
  那是镜头在动，不是"有人闯进来"。
  她本来就画在 OS 层**之上**（立绘 `z-index` 9997 > `#animus` 9000），
  所以"她穿过去"在层次上本来就成立，动画只是把它演出来。
- **故障那部分是**复用**的**：外壳本来就有那套（`#animus.scan` → `.ax-tear` 撕裂条 /
  `.ax-scanbar` 扫描线，换层时用的就是它）。`boot.js` 通过 `Animus.glitch()` 调它
  —— 与其在调用方把 `.scan` 那三行抄一遍，不如从外壳开一个口子。
- **为什么要"演完再发"**：C# 换场景要时间。先发消息的话，网页这一层先消失，
  玩家看到的是"菜单没了、画面还在原地"。发晚了没关系：换场景的耗时正好接在这段动画后面。
- **游戏页的 `#handoff-veil` 不带 `covered`**（保持透明）：切换那一段是 Unity 那层光
  盖着的（它等网页 `ready` 之后才坠下去），所以 UI 是随着光落下自然露出来的。
  `app.js` 的 `dropHandoffVeil()` 仍然管着 `handoff-arriving`（界面落位那套动画）。
- **三个入口走同一条路**：开始游戏 / 继续游戏 / 章节跳跃（`menu.chapter` 也会换到
  MainRoom）。都经过 `menu/boot.js` 的 `leaveToGame()` —— 不走它就会有一条是硬切。
- 浏览器里预览时**不演**：没有宿主，`leaveToGame` 直接返回（否则菜单会淡掉
  然后永远停在淡掉的状态）。

> ⚠ **时长**：`boot.js` 的 `LEAVING_MS` = 520ms，必须和 `menu/menu.css` 的时间轴一致。
> 那层光**两个方向的时长刻意不同** —— 亮起来 180ms（+190ms 延迟，"炸开"）、
> 收掉 240ms（"穿出来"）。所以它们不在 `theme.css` 的基础规则里，
> 而在各自的样式表里覆盖。
>
> ✅ **反方向（游戏 → 主菜单）走同一套**：游戏页也是**先升光、再发消息**
> （`app.js` 的 `leaveToMenu()` 加 `leaving-to-menu` + `covered`，时长在 `style.css`），
> C# 在那片主题光里换场景，主菜单场景的 `ChapterTransition` 补上动态。
> 四个出口都走它（暂停菜单那颗「回主菜单」、暂停菜单瓦片里的那颗、控制条上那颗、M 键），
> 300ms + 少量保持，和 `LEAVING_TO_MENU_MS` 对齐。
> 退出游戏（`menu.quit`）**不走**它 —— 那是退出进程，不需要过场。

### 主菜单的立绘：在网页里，不在 Unity 场景里

主菜单的版式是**左边选项、右边立绘**。立绘由 **`oh-my-live2d`** 在**网页里**渲染
（`menu/live2d.js`），Unity 场景完全不参与。

**所以 `MainMenu.unity` 不需要任何立绘** —— 它是"相机给一层背景色 + 一个 WebView"，
就这些。

> **为什么走网页而不是把立绘搬进场景**：立绘预制体 `Assets/Prefabs/Characters/2-3.prefab`
> 里**所有物体都在 layer 0**，而 MainRoom 的 `Live2D Camera` 只渲染 **layer 6**。
> 所以 MainRoom 的场景文件里有**约 670 条 `m_Layer: 6` 覆盖**——它们是必需的，不是美术微调。
> 加上 `WanXuanLive2DController` / `GazeFollowController` 是加在预制体子物体上的，
> 还有一批指向预制体内部组件的 stripped 引用。手写 670 条 layer 覆盖 + 交叉 fileID 引用，
> 正是本项目上次"整个界面点不动"那类事故的成因。
>
> 换成网页渲染之后这些全都不存在，而且悬停菜单项 → 她换表情是同页面直接调，没有桥接延迟。

配置基线来自 `D:\NekoClaw\PersonalPage\index.html` 里一份**跑通过的**同模型配置
（那边模型在 `l2ds/宅久/`，这边由 `WebUiServer` 挂在 `/models/` 下）：

```js
OML2D.loadOml2d({
    initialStatus: 'sleep',
    dockedPosition: 'right',
    models: [{
        path: '/models/2-3.model3.json',
        position: [-40, 60],      // ← 位置
        scale: 0.08,              // ← 大小
        stageStyle: { height: … } // ← 舞台高度（最主要的"她多大"旋钮）
    }]
});
```

`TUNING` 那三个数是**主菜单的构图**（半身），它没有变、也不该变 ——
全身只在「设置 → 立绘」那一页临时切过去（见下面「取景：半身还是全身」）。

**前提：必须通过 Unity 的 `WebUiServer` 打开本页。** `oh-my-live2d` 要用 `fetch`
读 `.moc3`，`file://` 下一律被拒。直接双击 `menu/index.html` 时菜单能显示、
立绘不会出来，右下角会有一条说明（`live2d.js` 检测到 `file:` 协议就显示它）。

> 顺带：`MainMenu` 的主相机 culling mask 我之前改成了 `m_Bits: 4294967231`
> （"全部除了 Live2D"）。立绘不进场景之后这是**空操作**，留着无害；
> 想让场景彻底回到原样，改回 `4294967295` 即可。

#### 取景：半身还是全身（`FRAMING`）

**主菜单是半身，只有「设置 → 立绘」那一页是全身。** 这是刻意的分工：

- 主菜单的构图是"她占右侧、不抢戏"，标题和那摞瓦片在左边 —— 所以 `TUNING`
  那三个数（`[700, 120] @0.30`）**不动**，主菜单永远用它们。
- 「立绘」那一页不一样：那一页就是在**调她**（亮度 / 饱和度 / 显不显示），
  而"调她"的前提是看得见她整个人。所以进那一页切全身，退出来切回半身。

顺带说明一件事：模型本来就是**全身**的 —— `2-3.cdi3.json` 的部件表里有
`腿左 / 腿右 / 拉链 / 裤绳 / 袖`，参数里有 `Param26 膝`、`袜子物理`、
`蝴蝶结(裤绳鞋带)物理`。所以"只看得到上半身"不是资源问题，是取景问题。

**谁决定切哪一档**：`boot.js` 的 `PAGE_MOODS.portrait.fullBody` ——
和表情、姿态放在同一张表里，因为它就是"这一页她该是什么样"的一部分。

**为什么全身必须动 `model.scale`，不能靠姿态那一层 CSS 缩放。**
画布只有舞台盒那么大（16:9 铺满视口），半身取景下她的下半身是画在画布
**外面**的 —— 那部分根本没被渲染进去。用 CSS 把 canvas 缩小只会把上半身
缩小，下半身依然不存在。只有改模型自己的 scale（pixi 那一层）才行。

`live2d.js` 的做法是"**算出来 + 量一次兜住**"：

1. 算目标值：pixi 的 Container 绕 `model.position` 那个点缩放，所以
   `新框 = position + (旧框 - position) × 缩放比`，由此反解出目标 scale 和位置
   （动画中途量到的只是中间态，没法当目标，所以这一档必须是算的）；
2. 520ms 插值过去（和 Animus 推门那 0.5s、姿态那 0.55s 同一个节奏 ——
   半身↔全身是**两倍**大小差，硬切会像画面被撕了一下）；
3. 动画停下之后**再实量一次**，把残差补掉 —— "缩放绕哪个点"这个假设
   没有实测过，落点因此是量出来的。

控制台里调（不用改代码，幂等）：

```js
VN.character.setFraming(true, 1.05)   // 全身；数字 = 她占画布高度的比例
VN.character.setFraming(true, 0.88)   // 全身，小一点
VN.character.setFraming(false)        // 回主菜单那套半身
```

进立绘页时会打一行日志，里面有实测框（左/上/右/下）、画布尺寸和视口尺寸。

> **如果她看起来悬在半空**（量到的框下缘不是她的脚，画布底部有留白）：
> `FRAMING.bottomGap` 填个负数（比如 `-0.04`）就把她踩到底了。
>
> **如果她偏大/偏小**：用上面那条命令换个数试，或改 `FRAMING.fullBodyFill`（0.94）。

两个边角：

- **窗口比例**：`fill / gap` 都是**画布**的比例而不是视口的。目标环境里两者
  相等；窗口一变就不等了 —— 舞台盒是"视口高 × 16:9"、右对齐，可能比视口宽。
- **resize**：库会按 `TUNING` 重新摆一次模型，把我们的取景覆盖掉，
  所以 `live2d.js` 在 `resize` 上延后 250ms 重做一次（等库先跑完）。
- **模型还没就绪就进了立绘页**：`setFraming` 会自己重试（500ms 一次，
  最多 10 秒）—— 调用方只在"她该是什么样"变化时才会调它，
  没有理由为一个"还没加载完"再调一遍。

> `getBounds()` 给的是模型这个显示对象的包围盒，**可能不是紧贴绘制像素的那个**
> （Live2D 的画面在 WebGL 里画，pixi 未必知道紧致的范围）。两种都能用：
> 画布本来就是照着这个人裁的。对着日志看一眼就知道是哪种 ——
> 她的头顶到脚该刚好落在那个框里。

### 为什么用 AutoInstall 而不是在场景里挂组件

因为**手写 Unity 场景 YAML 时，引用一个"还没被 Unity 导入过"的脚本 GUID 是做不到的** ——
GUID 要等 Unity 导入 `.cs` 文件才会生成。而 `[RuntimeInitializeOnLoadMethod]` 让组件自己找上门，
正好绕开这个限制。

代价：这些组件的 `[SerializeField]` 字段**改不了 Inspector**（运行时创建的对象没有 Inspector）。
要改就在代码里的字段初值改。想让策划能改，可以手动把组件加到场景里的 UWB 物体上 ——
AutoInstall 发现有现成的就不会再建一个。

涉及五个自动挂载组件（都在 `Assets/Scripts/UI/`）：

| 组件 | 干什么 |
|---|---|
| `WebUiServer.cs` | 本机 HTTP 服务，并把 `initialUrl` 改写成 `http://localhost:端口/`（`/models/` 挂载见上文） |
| `WebUiBridge.cs` | 建立与页面的双向通道（消息队列、主线程派发、握手、**ready 闸门**） |
| `WebInputFix.cs` | 接管鼠标 / 键盘转发（UWB 自带的输入层有缺陷，见下文） |
| `WebSettingsChannel.cs` | 设置的读写通道（`settings.request` / `settings.changed`） |
| `WebSceneFlow.cs` | 场景流转（`menu.start` / `ui.menu` / `menu.quit`）+ 下发主菜单标题 |

#### 挂载要覆盖**每个场景**，不是只有启动场景（`UwbAutoInstall.cs`）

`[RuntimeInitializeOnLoadMethod(AfterSceneLoad)]` **一次运行只触发一次**，只覆盖启动时的第一个场景。
本工程是运行时切场景（MainMenu --「开始游戏」--> MainRoom，回去同理），新场景里的 WebView 是**全新对象**
（叫 `BrowserController`），老的那台连同挂在它上面的组件一起被销毁。

后果在日志里一目了然：`[WebUiBridge] AutoInstall：场景=` 一直是 `MainMenu`，
游戏场景里一个组件都没有 —— 网页跑在 **standalone**（自己放本地 `story.js`）。
表现上"能玩"，但 C# 那条链在游戏里其实是断的：**继续游戏续读到存档步、章节跳跃、
文字速度等设置下发，全都到不了游戏页**。

所以挂载统一走 `Assets/Scripts/UI/UwbAutoInstall.cs`：各组件在自己的 `AutoInstall` 里
`UwbAutoInstall.Register(...)`，它**立即执行一次**（等价原来的 AfterSceneLoad），
并挂上 `SceneManager.sceneLoaded`，此后每次场景载入都重跑。安装函数靠各组件里已有的
`GetComponent<T>() != null` 判重，所以是幂等的。
`sceneLoaded` 在场景对象的 `Awake/OnEnable` 之后、`Start` 之前触发，而 UWB 是在 `Start` 里
把 `initialUrl` 当命令行参数交给 CEF 引擎的 —— 所以改写仍然早于引擎读参数，不会先按 `file://` 载一次。

> ⚠ **这件事和 `WebUiBridge` 的发送闸门是一套，不能只做一半。**
> 游戏场景一旦有了桥，C# 就会开始往这个页面推剧情 —— 而推早了会**静默丢掉**（见下一节）。
> 只做挂载、不做闸门的实测结果就是：开场四条全丢，玩家看到空白对话框、点一下直接到第二句。

#### 发送闸门：等网页的 `ready`，不等"引擎就绪"

`ReadySignalReceived` 是**引擎级**信号（`WebBrowserClient.cs` 里那句 "UWB startup success, connecting…"），
它只说明 CEF 进程起来了 —— 那时候网页脚本可能还没跑完，`window.__vnReceive` 还不存在，
消息会被 v8 执行成 `Uncaught TypeError: window.__vnReceive is not a function`，然后**静默丢掉**。
实测（只挂载、没闸门）丢的正是开场四条：握手 / `story.load` / 幕标题 / 第一句。

所以 `WebUiBridge` 的发送多等一个条件：网页自己发来的 `ready`
（游戏页在 `app.js` 的 `init` 收尾、主菜单页在首帧之后；两页都是**先注册订阅者、再发 ready**，
所以收到它就等于"发过去有人接"）。另有 3 秒兜底 —— 页面改了忘了发、或者启动时抛了异常，
也不能让剧情一句都发不出去（那种情况会打一条 warning）。

## Animus 归档系统：设置页 + 暂停菜单（`animus/`）

这是**第三套界面系统**。它的**结构与动效**来自《刺客信条 2》的 Animus Desktop（按 `Esc` 呼出的暂停菜单）：
一个固定空间 + 一台会走的镜头、发丝级细线、零圆角、方形叠片导航、左导轨 + 中间内容 + 底部详情。
原版那套「白房间 + 灰骨架 + 砖红的位置信号」是 AC 自己的配色，我们换成了**她家客厅的光**
（四套，见下），所以它和主菜单那间暖房是同一个世界。

**结构不是 DNA。** AC2 那套界面的底子是"翻阅血脉档案"，所以原版画的是一条双螺旋。
**我们这里没有那条线** —— 剧本里从头到尾没有血缘、没有遗传、没有族谱，硬套过来只会让人以为要讲这个。
所以双螺旋连同它的横档（梯子）**整个删掉了**：现在只剩**一根索引绳**，没有第二条链，也没有横档。

> 这一条是**已经定了的**，不是"待定"：隐喻是**归档**，用剧本自己的词，
> 出处与取舍见下面「和剧本的统一（**已定：归档**）」那一节。
> 文档里还留着 DNA 字样的地方，都是"以前是什么、为什么删掉"这类说明本身。

### 配色（**四套，一套就是客厅的一种光**）

整套界面的颜色只在 `animus.css` 顶上那**四块主题变量**里
（`#animus` / `[data-theme="noon"]`、`[data-theme="evening"]`、`[data-theme="lamp"]`、`[data-theme="rain"]`），
组件规则一行都不含颜色。四块的分法一律是两层：
**空间层**（底、网格、点阵、数据流、暗角、瓦片材质）决定"这是个什么样的地方"，
**内容层**（字、线、位置信号、数据色）决定"东西怎么读" —— 换主题基本只动空间层。

这四套**不是"四个好看的配色"**（原来那三套 `warm` 暖木 / `cream` 奶油 / `dusk` 暮蓝 就是那种，
已经删掉了），是**场景需求表里那四张客厅**。那张表的高优先背景前三张就是
「客厅-午后晴 / 客厅-傍晚暖光 / 客厅-夜小灯」，加上「客厅-雨夜」正好四张；
表里还写着"客厅建议至少做 5 套光照变体"。所以主题 = **客厅的光照变体**，
取色依据全部是剧本自己的【场景】/【BG】原话：

| id | 名字 | 依据（剧本原话） | 覆盖哪一段光 |
|---|---|---|---|
| `noon` | 午后 · 晴 | 1-1【场景】客厅 / 午后 / 晴【BG】**大客厅，大片落地窗，光线安静地落在地板上** | 1-1 寂静的独居生活 / 1-3 借宿协商 / 2-3 午后下午茶，以及 **5A-3 与 5B-3 两个结局的收束**（5B-3 的【BG】是「同样的客厅，安静但不空」） |
| `evening` | 傍晚 · 暖光 | 1-4【BG】**夕阳染色的餐桌**；4-2【BG】天色压暗，室内亮灯，锅中热气明显 | 1-4 第一顿正式晚餐 / 4-2 最后一顿普通晚餐（同一个傍晚，**一头一尾**） |
| `lamp` | 夜 · 小灯 | 2-4【BG】**只开一盏小灯的客厅与厨房**；3-1【BG】夜色中的客厅…**电视微亮**；3-4 电视熄灭后的小灯单点照明 | 2-4 深夜煮面 / 3-1 初夏夜宵 / 3-2~3-4 直播。**默认主题** |
| `rain` | 雨夜 · 冷光 | 4-3【场景】客厅 / 夜 / 雨声不止；4-1【BG】天色压低，屋内昏暗，阳台外风大；3-5【场景】阳台 / 凌晨【BG】城市夜景，风稍大，**月色冷淡** | 4-1 召回（雷雨将至）/ 4-3 选择前夜 / 5A 与 5B 的高潮 |

序章和两个结局收在**同一束午后** —— 这是脚本自己写的呼应：5A-3 与 5B-3 的【BG】都是"午后 / 晴"。

默认那套是 **`lamp`（夜 · 小灯）**（`data-theme` 不设或 `"lamp"`）。主菜单、设置、暂停菜单
第一眼看到的都是它。底几乎全黑，只有一处暖光源 —— 而那团光就是**她光环的金**：

| | 取色 | 用在哪 |
|---|---|---|
| **夜·近黑的暖褐** | `#1C120C → #2A1B13 → #3E2820` | 空间本身 |
| **暖白**（`--ax-ink`） | `#FFF7EA` | 字、线、骨架 —— 不是纯白 |
| **她光环的金**（`--ax-mark`） | `#F2D06B` | **位置信号**：选中瓦片 + 标签后面那条实心横条、对焦线、空间连线、跑动的亮弧 |
| **她身上的淡雪青**（`--ax-cyan`） | `#A9B8E8` | 数据：REC 号、kicker |

> **`--ax-mark` 是这套配色的核心决定。** AC 用砖红标记"当前"，那是
> *系统在标记你*；金是 *她在看着你*。她身后那团光（`--ax-bg-glow`）
> 用的是**同一个金**（`rgba(242, 208, 107, 0.18)`）—— 所以 `lamp` 这套里 UI
> 不是贴在画面上的另一层，是被她那盏"小灯"照亮的：2-4 的【BG】就是"只开一盏小灯"。

#### 位置信号**永远取自她身上，不取自屋子**

`场景需求表` S02 对她的造型只写了一行：**「白色长裙、长发、半透明羽翼、头顶淡金色光环」**。
所以每套主题的"你在这里"色只可能是这三样之一：

**光环的金 · 半透明羽翼的白 · 发梢的淡雪青**

挑哪一个只有一个判据：**在这间屋子的光里，哪一样最跳得出来。**

| 主题 | 位置信号 | 为什么是它 |
|---|---|---|
| `noon` 午后 | 光环的金**压深成琥珀** `#9A5B12` | 白天那圈金不发光，浅金会糊在墙上（`#F2D06B` 那么浅读不出来），压深才立得住。**压到多深是量出来的**，不是挑的：金上要压字（`--ax-mark-ink` 是米白），这一对得够 4.5:1，`#B8862B` 只有 3.2:1 |
| `evening` 傍晚 | **羽翼的白** `#EAF2FF` | 满屋都是橙的，**只有她是冷的** —— 这也是这一场戏的意思 |
| `lamp` 夜 | **光环的金** `#F2D06B` | 满屋黑，那盏"小灯"就是她的光环：她说"我在这里" |
| `rain` 雨夜 | **月下的羽翼冷白** `#B9C8EE` | 而且这里和其它三套**反过来**：金退到数据色（`--ax-cyan` = `#E8C97A`），只剩**极小的一行记录号** —— 整间屋子冷到底，那一行金是唯一还暖着的东西（那是她还没走） |

每套都只有**两个**强调色：位置信号 + 数据色（`--ax-cyan`，跑 REC 号、对焦线、空间连线那类"系统数据"）。
加第三个就没那个味道了 —— 别的主题也不是加色，而是**把这两个的角色对调**
（`evening` 是金→数据 / 羽翼白→位置，`rain` 是金→数据 / 冷白→位置，两套都真的对调了）。

四套是**同一副骨架换空间层和位置信号色**，用设置页「显示」子页那一行「界面主题」切
（值是 `noon` / `evening` / `lamp` / `rain`，落盘走 C#）：

- **`noon` 午后 · 晴**（亮底反面）：底是落地窗那一片白 → 木地板被晒暖的米
  `#FCF7EE → #F6EEE0 → #EADFCB`，`--ax-ink` 是木褐 `#4A3A2A`（**午后没有真正的黑**）。
  参考图那套深底的经验在这一套里几乎全是反的：连"高光"都要反过来变成暗色
  （`--ax-flash` = `#8A6247`、`--ax-flash-blend: multiply`，见下面「各给自己的那四个变量」）。
- **`evening` 傍晚 · 暖光**：四套里唯一一套**饱和的暖色** `#2A1409 → #4A2410 → #7A3C14`
  （起头那半边已经暗下去，收尾那片窗子是烧起来的）。和 `lamp` 那种发黑的暖褐不一样：
  一个是被太阳照的，一个是被一盏灯照的。
- **`rain` 雨夜 · 冷光**：和 `lamp` 是**两套不同的暗** —— `lamp` 是暖褐的近黑（屋里有一盏灯），
  `rain` 是冷灰蓝的近黑（屋里没有灯，光是从窗外来的）。所以连数据流的收尾色
  都从暖白换成冷白 —— 雨夜里不存在暖白这种东西。

**换主题只动这四块。** 组件规则里一个颜色都没有 —— 所以加第五套主题的代价是**再写一块变量**，
不是满文件找颜色。

### 主题要真能换：**canvas 的颜色也必须走变量**

CSS 是 `rgb()` 字符串，canvas 要的是 `34,48,58` 这种**裸通道三元组**，
拼不出来。所以主题块里额外给了 `--ax-ink-rgb` / `--ax-mark-rgb` / `--ax-cyan-rgb`，
`animus.js` 的 `readTheme()` 读它们，缓存在 `INK` / `MARK` / `CYAN` 三个变量里。

**现在有两个地方会调它**：`open()` 时读一次（第一次掀开界面），以及**换主题时**
（`settings-module.js` 的 `applyAnimusTheme()` 在改完 `data-theme` 之后调
`Animus.refreshTheme()` —— 那就是 `readTheme`）。上一版这里只有 `open()` 一处，
因为那时**没有换主题的界面**；现在「显示」子页里那一行「界面主题」就是，
所以必须有第二个入口，否则选完主题画布会留在上一套配色里。

> **踩过的坑**：这三个一开始是写死的。换成深色主题之后，
> **画布上那条绳直接消失了** —— 组件全换了色，画布留在上一套配色里，
> 从代码上完全看不出来。凡是 canvas 画的东西都要走这三个变量。

另外三条：

- **同一个 alpha 在浅底和深底上差很远**：浅底上 0.12 的深色是一块灰，
  深底上 0.12 的浅色几乎什么都没有。绳取的是两边都能看的中间值
  （`done` / `open` / `locked` 三档分别是 0.40 / 0.16 / 0.18）。
- **轮廓比填充更重要**：填充随进度状态变淡（`open` 是最淡的一档），
  轮廓（`ink` 0.45）是"形状"的兜底 —— 没有它，进度未知时整条绳会消失。
- **数据流是"会动的东西"里唯一没有剧本依据的一层**：14 条 1px 往下淌的细线，
  纯粹是"这台机器在跑"的意思（和右上角那个跳动的读数同一个用途）。
  背景里别的会动的（那团光、网格的极慢漂移、canvas 那层绳）都是屋子里的。
  中间试过两版"光"（26 条硬边竖条 / 4 道宽柔光柱），都撤了 —— 那是从 AC
  参考图抄的形状，剧本里没有依据。

#### 四套主题各给自己的那四个变量（`--ax-flash` / `--ax-flash-rgb` 是同一个色，表里分两行）

上面那条"canvas 通道三元组"只解决了**画布**。做第三套主题的时候又翻出来三个
**写死的颜色**，它们都属于同一类错误：**"比周围更亮"的东西，在亮底上必须反过来变成"更暗"。**
加第四套主题时又多出第四个（`--ax-gold`，见下）。

| 变量 | 午后 | 傍晚 | 夜（默认） | 雨夜 | 用在哪 |
|---|---|---|---|---|---|
| `--ax-tile-shadow` | `rgba(150,116,84,0.34)` | `rgba(28,10,2,0.55)` | `rgba(42,27,19,0.55)` | `rgba(2,6,14,0.6)` | 选中瓦片下缘那条"厚度"阴影 |
| `--ax-flash` | `#8A6247` | `#FFEBD2` | `#FFF7EA` | `#EAF1F8` | 滑杆旋钮外面那圈光环 |
| `--ax-flash-rgb` | `138,98,71` | `255,235,210` | `255,247,234` | `234,241,248` | 数据流末端、扫描线顶端的渐变收尾 |
| `--ax-flash-blend` | `multiply` | `screen` | `screen` | `screen` | 那条横向扫描光的 `mix-blend-mode` |
| `--ax-gold` | `#C08F2E` | `#FFD79A` | `#F2D06B` | `#E8C97A` | 滑杆悬停时旋钮的暖色强调 |

- **`--ax-tile-shadow`** 原来是写死的 `rgba(90,14,12,0.55)` —— 砖红时代的残留。
  暖木（当时的默认）上它是深棕、看着还行，换到现在叫 `noon` 的那种浅底（当时叫「奶油」）就变成**一块脏红压在浅色瓦片底下**，
  一眼就看出没跟着换。要的是"比瓦片本身暗一档的同一个色系"—— 四套现在的值都取自**各自那块底**
  （午后＝它的网格褐 `150,116,84`、傍晚＝它的背光近黑 `28,10,2`、夜＝`--ax-bg-mid` 那个暖褐 `42,27,19`、
  雨夜＝它的冷光近黑 `2,6,14`）：**跟着底走，不跟位置信号走**。
- **`--ax-flash` / `--ax-flash-rgb`** 那三处原来写死纯白。深底上是对的，
  浅底那一套（当时叫「奶油」，现在是 `noon`）上整个消失 —— **白压白**。
- **`--ax-flash-blend` 是最后才发现的一处**：光写对颜色还不够，
  `mix-blend-mode: screen` 在亮底上**等于没有**（`screen(x, 近白) ≈ 近白`），
  而浅底那套的底本来就接近白。亮底上要换成 `multiply`：同一道"更亮的光"，
  在亮底上表现成"更暗的一道影子扫过去"，读起来才还是"有东西过去了"。
- **`--ax-gold` 是这一轮换主题时翻出来的漏网之鱼。** 它原来是"哪套想要就自己写一条"，
  旧的三套里**只有两套**声明了它 —— 而**默认那套正好是没声明的那个**，
  于是滑杆旋钮悬停 / 获得焦点时（`input[type="range"]:hover::-webkit-slider-thumb`）
  那条 `background: var(--ax-gold)` 在当时的默认那套（暖木）上引用了一个**不存在的变量**：
  按 `var()` 的规矩这条声明整条失效、属性退回初始值，所以悬停时不是"变暖"，
  而是**丢掉 `background`**。不报错、页面也不崩 —— 只有某个主题上的某个交互静默地不对，
  而且因为默认那套恰好就是缺它的那套，等于**所有人第一眼看到的都是坏的那个**。
  现在四块都声明，同时删掉了没人引用的 `--ax-gold-wash`。**四块现在各声明同一组 34 个变量**
  （数过）—— 少一条就是"某个主题上某处静默失效"这类 bug，所以加主题时先对着四块 diff 一遍变量名。

> 排查手法：把主题切一遍，然后在 `animus.css` 里搜**不带 `var(--` 的 `rgba(` / `#`**。
> 剩下的命中应该只有两类可以放过：alpha 是 0 的渐变收尾（RGB 通道无意义），
> 以及 `mask-image` 里的黑色（遮罩只看 alpha）。
> 其余每一条都是"忘了跟着主题走"的候选。

#### 四套的对比度都量过（**亮底那一套最容易翻车**）

配色不是挑好看就完了 —— 四套的底不一样亮，同一组 alpha 落到不同的底上，
对比度差得很远。所以每套都按 WCAG 算过一遍（正文 ≥ 4.5:1，最小那档辅助字 ≥ 3:1）：

| 要读的东西 | 午后 | 傍晚 | 夜 | 雨夜 | 需要 |
|---|---|---|---|---|---|
| 正文 `--ax-ink` / 底 | 9.44 | 11.65 | 15.61 | 14.74 | 4.5 |
| 次要 `--ax-ink-soft` / 底 | 6.40 | 6.22 | 7.46 | 6.75 | 4.5 |
| 极小 `--ax-ink-faint` / 底 | 3.77 | 3.31 | 3.61 | 3.47 | 3 |
| 数据色 / 底 | 5.30 | 9.03 | 8.47 | 10.45 | 3 |
| 位置信号上的字 / 位置信号 | 5.32 | 15.50 | 11.08 | 11.40 | 4.5 |
| 数据色上的字 / 数据色 | 6.00 | 11.65 | 9.38 | 10.45 | 4.5 |

**`noon` 第一版是不过的**，而且不是差一点：`--ax-ink-soft` 3.41、`--ax-ink-faint` **1.91**、
位置信号上的字 3.18、数据色上的字 3.83。原因是**亮底和深底的方向是反的**：

- 深底上"让字淡一点"＝往暗处让，掉得慢；
- 亮底上"让字淡一点"＝**往底色（白）靠**，掉得极快 ——
  `rgba(74,58,42,0.36)` 压在米黄上只有 1.9:1，那就是看不见。

所以四套里 `--ax-ink-soft` / `--ax-ink-faint` 的 alpha 差别很大（午后 0.86 / 0.66，
另外三套 0.62~0.68 / 0.40~0.42）。**给亮底主题调"淡色"时别照抄深底那套的数。**
`noon` 的位置信号也因此从 `#B8862B` 压到 `#9A5B12`（金上压米白字要够 4.5:1）。

> 这段的算法很简单，改完配色重跑一遍就行：把每个变量解析成 rgb、按 alpha 合成到底上、
> 算相对亮度比。**别靠眼睛判断"够不够清楚"** —— 我第一版就是靠眼睛，
> 结果 `noon` 那一套的辅助字有一半是读不出来的。

  1px 细线（`.ax-stream`，纯 CSS 动画，没有 canvas）。
  中间试过两版"光" —— 26 条硬边竖条、4 道宽柔光柱 —— 都撤了：
  那个形状是从 AC 参考图抄的，剧本里没有依据。

它单独成一套而不是塞进 `menu/` 的理由：**它在两个地方都要出现**。

| 入口 | 在哪个场景 | 打开方式 | 有几页 |
|---|---|---|---|

这类不一致。**内容分模块注册，框架不认识内容**：加一个"人物档案"只要再写一个 module 文件。

### 坐标系是第三套，这是刻意的

`#animus` 挂在 `document.body` 上、`position: fixed`、全部用 `vw`/`vh`：

- 游戏页的 `#stage` 是 1920×1080 等比缩放，非 16:9 时四周有黑边。暂停菜单是"跳出游戏"的一层，
  它不该跟着游戏画面一起缩进黑边里。
- 主菜单页的 `#stage` 是全视口、右侧立绘按视口像素定位。用视口坐标才和立绘对得上。

UWB 里 CEF 的视口恒为 1920×1080，所以 `vw`/`vh` 就是设计值本身。

z-index 是 **9000**：在两边所有界面之上，但在**立绘之下**（立绘是 9997）。
打开设置时她还在，只是被默认那套（**夜 · 小灯**）的底和**她光环那团金**的光洗过一遍
—— 这一条是刻意的：那团光就是她本人。

> **踩过的坑：`position` / `z-index` / `opacity` / `visibility` / `pointer-events` / 过渡
> 一度被塞进了某一个主题块里。** 它们原本躺在 `[data-theme="dusk"]` 那一块末尾
> （大概是加第三套主题时顺手追加到主题段落最后的），后果是"这些行为只有那一套主题才有"，
> 两条都是量出来的：
>
> - 只有那一套是 `position: fixed`，另外三套退化成 `static`。于是绝对定位的
>   `.ax-backdrop` 只好去找最近的一个**定位祖先** —— 游戏页那个是 `#stage`
>   （量到 `#stage { position: absolute }`、`#animus` 的 rect 是 1920×**0**），
>   暂停菜单又被缩回 16:9 的信箱里，而"用视口坐标、跳出 `#stage`"正是第三套坐标系存在的全部理由。
> - 更糟的是只有那一套有 `opacity: 0` + `pointer-events: none`，另外三套**关不掉**：
>   按 `Esc` 继续游戏之后暂停菜单还留在屏幕上，还继续吃掉鼠标点击（截图里能看到它压着对话框）。
>
> 现在这些都回到基础 `#animus` 块里，四套主题一律是 `position: fixed` / `z-index: 9000` /
> 1920×1080，关掉时一律 `opacity: 0` + `visibility: hidden` + `pointer-events: none`。
> 教训：**一个属性写进主题块，就等于"这个行为只在这一套主题下存在"**；
> 加主题时往那个 block 里追加的应该是**变量**，不是结构。
> （换个说法：主题块只能装颜色，装不了行为 —— 装进去的那一刻，它就变成了"某一套主题的功能"。）

### 空间 + 相机：这一节是整套界面的核心

前两版都没做对，值得写清楚区别：

| | 读起来是 |
|---|---|
| 第一版 | 等距竖排的方块 + 旁边画一条螺旋（那时抄的还是 DNA 的形状）→ **选项卡列表** |
| 第二版 | 节点骑在那条螺旋上 → 选项卡列表，但每条上挂了个点 |
| 现在 | **一个固定空间 + 一台会走的镜头** → "我在 Animus 里" |

区别不在绳画得好不好看，而在**切子页时到底发生了什么**。
前两版是"换一屏界面"（幻灯片），现在是"镜头沿绳滑过去"。

**场景和取景框是两样东西：**

```
.ax-rail        取景框   overflow: hidden，本身不动
  .ax-focus-line  对焦线   在取景框正中，**不跟着相机走**
  .ax-rail-cam    场景     上下各多出 15%，只有它的 transform 被每帧改写
    canvas + 节点
.ax-connector   空间连线  从对焦线横穿到内容列，**静态**
```

- 切子页 = `pan = (0.5 − 节点在场景里的 u) × 场景高`，把选中节点送到对焦线上
- 同时 `scale` 用 `sin(πt)` 推近 5.5% 再收回 —— 纯平移看不出"推近"，加这一下才有镜头感
- 首开直接就位不放滑动：开场那一下滑动会让人以为"刚才在别的地方"
- 对焦线两端有直角小括号，是镜头对焦框的记号

**一根空间连线（`.ax-connector`）是"绳和面板在同一个空间里"的全部证据。**
没有它，左边是导航、右边是内容，两块仍然是拼起来的。

**`span ≤ 0.385`（overscan 0.15），这是硬约束不是审美。**
相机是把选中节点送到 `u = 0.5`，而取景框只看得到场景的
`u ∈ [0.115, 0.885]`。最远的节点会落在 `0.5 + span` 上，要让它留在画面里就得
`span ≤ 0.885 − 0.5`。

**`overscan` 的旧值是 `0.32`。** 换成 0.15 的理由是**这条不等式**：`o = 0.32` 时
`span` 的上限只有 0.305，而桌面上的条目从 5 个涨到 7 个，0.305 装不下 ——
把 `o` 降到 0.15 就把上限抬到 0.385，换来的可用 span 正好够排 7 格。
它**不是**为了好看才改的，改回去就要同时把条目数降回 5。

**而且 `overscan` 只能有一份。** 它本来在 CSS（`.ax-rail-cam { top/bottom: -15% }`）
和 `CFG.overscan` 里各写了一遍，我把 CFG 改成 0.15 却忘了改 CSS ——
结果节点按 871px 摆、画布却是 1098px，选中最后一个条目时头两格直接跑出画面。
现在 `camHeight()` 直接读 `el.railCam.clientHeight`，**只留 CSS 那一份**。

条目变多时（参考图那摞有十个左右）先动 `.ax-node` 的行高，再动 span；
两个都要动的时候记住上面那条不等式。

### 背景那一层大绳

`.ax-space`，铺满全屏、比导轨那条大得多淡得多慢得多，画在所有内容**下面**。
"无论你在哪个子页面，背景里总能看到绳的局部在缓缓荡动" —— 这一层就是那句话。
有了它，四个子页才像"同一个空间里的四个机位"。

它和导轨那条是**两套参数**（`CFG.space` / `CFG`），因为一个是环境一个是导航：

| | 中轴 | 摆幅 | 荡几个来回 | 周期 | 透明度 | 采样步长 |
|---|---|---|---|---|---|---|
| `CFG.space`（环境） | `x: 0.40`（占视口宽） | `0.20` | `0.55` | `44s` | `0.26` | `6px` |
| `CFG`（导轨、导航） | `helixX: 0.34`（占导轨宽） | `0.17` | `0.9` | `34s` | 渐变（中段 0.46） | `2.5px` |

> 这两行的**摆幅不能用来看"哪个更弯"**：它们的分母不同 ——
> 视口宽 1920 的 `0.20` 是 ±384px，导轨宽 22vw（422px）的 `0.17` 是 ±72px。
> 环境那条在绝对像素上散得开五倍，这才是它在满屏画面上看得出形状的原因。

周期 `44s` 比导轨的 `34s` 慢三成、`cordAlpha` 压到 `0.26`：**它是背景，不该抢戏**。
采样步长 `6px` 也是同一个取舍 —— 它只是一层氛围，不用画细，导轨那条才需要 `2.5px`。

**纵向遮罩是必须的**：不遮的话它横穿标题和设置行，文字立刻读不清。
现在它在上下两条空白带里最实（mask 0.95）、穿过内容时压到几乎看不见（0.18）——
空的地方它负责空间感，有字的地方它让路。

它**每 3 帧才画一次**（约 20fps）。铺满全屏的 canvas 每帧重画在 CEF 里不便宜，
而它只是缓慢漂移的氛围。导轨那条绳是导航，必须每帧画。

> 这一层是**一根绳，没有第二条、也没有横档** —— 和导轨那条、和章节归档那条一样。
> 上一版这里是两条链加一根根横档（DNA 的两条链 + 碱基对），那个循环连同
> `drawRungs()` 一起删掉了，`CFG` 里的 `rungEvery` / `rungAlpha` 也一起没了。

### 节点位置的约束

节点的 **u 由高度决定**，横坐标再由 `nodeXAt(u, 荡的相位)` 求出来 ——
所以绳一荡，节点跟着左右游走，它是真的挂在绳上。标签留在原地用引线连过去
（标签跟着绳晃就没法读了）。

这条绳的四个数是**一起定的**，改一个要看另外三个：

| 参数 | 值 | 它决定什么 |
|---|---|---|
| `turns` | `0.9` | 从顶到底荡几个来回。**旧值是 3.4** —— 那个数是给双螺旋用的（要拧够圈数才像 DNA），一根绳拧 3.4 圈就是弹簧。0.9 才是"两端拉住、中间荡开"的一段弧 |
| `amplitude` | `0.17` | 摆幅（占导轨宽 22vw ≈ 422px，也就是左右各 ±72px）。**旧值 0.20**。节点挂在绳上，所以这个值同时决定"节点会左右游走多少"：调小就不像绳，调大会撞上右边的标签（标签的横向位置 `labelX` 是定死的 0.60） |
| `spinSeconds` | `34` | 荡一个周期的秒数。代码注释里的理由是"比旧链条慢，绳比螺旋重"；调小它不会改变形状，只会让"荡"变得像抖 |
| `helixX` | `0.34` | 中轴在导轨里的横向位置。名字里的 `helix` 是**历史的**，别按它去找螺旋 |
| `sampleStep` | `2.5` | 采样步长（像素）。它是导航，要画得比环境那条细（那边 6px） |

**只有一根，没有横档。** `drawRail()` 就是"从 y=0 到 y=H 按 `sampleStep` 取点、
每点用 `nodeXAt(u, spin, W)` 求横坐标、一次 `stroke()`"，`lineWidth` 1.8。
上一版这里是两条正弦（相位差 π）加一个 `rungEvery` 循环画横档 —— 那是 DNA 的两条链加碱基对，
所以两条一起删了。纵向的 alpha 走一条垂直渐变，绳在画面外自然消失，不用画端点。

> **别把这条改成"按序号排横向位置"。** 一改就变回选项卡列表，
> 而且这个错误从截图上很难看出来 —— 前一版就是这么错的。

换页时还有一段**亮弧沿着绳从旧节点跑到新节点**（`travel`，画在 canvas 里），
外加一颗跑在前头的光点。那是那套界面的招牌动作：光标在绳上移动，
而不是"选项卡被点亮"。

### 谁能动镜头，谁不能（**手感全在这一条上**）

第一版我用 `mouseenter` 驱动镜头，结果是**闭环**：光标悬停 → 镜头动 →
标签从光标底下滑走 → 光标落到下一格 → 又触发悬停 → 镜头又动。
现象是**鼠标停在原地，选项自己不停跳**。

两条规则治它：

1. **鼠标悬停不许动镜头**（`highlight(i, { camera: false })`）。
   镜头一动，你正指着的东西就会跑。
   - 鼠标悬停 → 只换高亮、右侧预览面板和立绘表情（见「悬停出口」那段）
   - 键盘 `↑↓` → 动镜头（键盘没有"指针被挪走"这回事）
   - 进入 / 返回 → 动镜头（推近 / 拉远）

2. **悬停挂 `mousemove`，不挂 `mouseenter`。**
   `mouseenter` 是"指针底下的元素变了"就触发 —— 而元素位置正是被镜头决定的。
   `mousemove` 只在**指针真的动了**时触发，闭环就断了。
   顺带解决另一个问题：键盘 `↑↓` 把高亮移走时，停着不动的鼠标不会把选择抢回去。

还有一条小的：`layoutNodes()` 把**行高直接取成格距**，让相邻两格严丝合缝。
不这么做行与行之间会留十来个像素的空档，鼠标滑过去高亮会「掉一下」——
手感上就是卡。

> UWB 那边不用额外处理：`WebInputFix` 走的是 `client.SendMouseMove(point)`，
> 由 CEF 自己做命中测试，所以 `event.target` 是正确的元素。

### 两级结构：桌面 → 子页 → 返回

**这是整套界面的骨架，不是"页面切换"。** 参考图里这两层差别极大：

```
第 0 层  Animus 桌面   选文件夹。左导轨 + 空间连线 + 右侧预览面板
第 1 层  子页          **每个文件夹自己的界面**，完全接管画面
```

- 光标在文件夹之间移动（鼠标划过 / `↑↓`）→ **只换右侧预览面板、镜头和立绘表情**，不进入
- 点击 / 回车 → 进入，镜头推近
- `返回` / `Esc` → 退回桌面，镜头拉回

**`Esc` 因此有**四**段，从里往外：** 第 1 层（内容页）→ 返回它所属的那屏桌面；
第 0 层但**栈非空**（子桌面，比如「设置」那一屏）→ 弹栈回上一屏桌面；
第 0 层且栈空 → 问调用方（外壳调 `Animus.handlers.esc()`：它返回 `true` 就是
"我自己处理了"，外壳**什么都不做**）；调用方不接 → 关掉。
玩家会按很多次 `Esc`，**只要还能往后退一层，`Esc` 就不是退出**。

> **第二段（子桌面）原来是漏的，而且它和底栏那颗按钮一起断，就成了死路。**
> 症状就是"设置页没有返回"：
> - `renderFooter(null)` 原来只有"有模块 / 没模块"两种分支，没模块就直接取
>   `frame.actions` —— 而主菜单那一摞的 `actions` 是**空数组**，所以进了「设置」
>   之后底栏一个按钮都没有；
> - `Esc` 在第 0 层又直接落到 `handlers.esc` 上，主菜单返回 `true`（= 什么都不做）。
>
> 两条路同时断，玩家点进「设置」就出不来了（只能点别的格子或者重开界面）。
> 修法是把"还能退一层吗"这件事**在外壳里判一次**，两处都用它：
> `backLabel()`（提示语）+ `renderFooter()` 的中间那条分支 + `Esc` 的中间那一段。
>
> **教训：「能不能退出去」不能只由底栏负责，也不能只由 `Esc` 负责 —— 两条路各自都要成立。**
> 而且新增一层导航的时候，要把"退出去"的三处（底栏按钮、`Esc`、提示语）一起想一遍。
> `Esc` 提示语也必须跟着层级变：进文件夹要说「返回」，退到根才说调用方给的那个词
> （主菜单是「关闭」）—— 写「关闭」却只退一层，玩家会以为按坏了。

两个调用方在这一段上的选择**不一样**，都是刻意的：

| 页面 | 第 0 层按 `Esc` | 为什么 |
|---|---|---|
| 游戏页（暂停菜单） | 关掉 = 「继续游戏」（`app.js` 没接 `handlers.esc`，外壳自己 `close()`；底栏那颗按钮写的也是「继续」） | 那是暂停菜单，`Esc` 的意思就是"我调完了" |
| 主菜单页（`boot.js`） | **什么都不做**（`handlers.esc` 直接 `return true`） | 它是标题画面：屏幕上能做的事只有"选一格"和"进去"，按一下就退出的行为会让人误触。要退出得选「退出游戏」或底栏那个「关闭」 |

> 上一版把两层压成了一层（导轨常驻、右边换内容），所以读起来是"选项卡"。
> 差别不在绳画得好不好看，在于**切页时到底发生了什么**。

进入 / 离开都靠镜头：`cam.enterAt` 打一个时间戳，`updateCamera` 在 `camMs` 内
叠一层 `sin(πt)` 的推近（14%）。它和沿绳的滑动是**叠加**的，所以读起来是
"一边滑一边推近"的一次动作，而不是两段动画接在一起。

### Animus 桌面**就是主菜单**

参考图里那一套本来就是"操作系统"：一摞瓦片里混着「继续」「放弃记忆」「离开」
这些**主菜单级**的动作。所以 `menu/index.html` 不再另做一个标题画面 ——
桌面本身就是主菜单：

```
-10 继续游戏（有存档才出现）→ -05 开始游戏 → 10 章节选择 → 50 设置 → 900 退出游戏
                                                  │
                                                  └─ 进去才是 20 声音 / 30 文字 / 40 显示 / 50 立绘
```

**设置是"一格瓦片"，不是四格。** 那四页挂在它的 `children` 上 —— 参考图的桌面里
「选项」也是一个入口，四页在它里面（见下面「导航栈」那一节）。
动作在最上最下、内容在中间，和参考图那摞瓦片的排法一致。

`boot.js` 打开桌面时是这样写的：

```js
Animus.open({
  kicker: '记 忆 归 档', title: '甜味的坠落',
  modules: ['continue', 'start', 'memory', 'settings', 'quit'],   // 顶层**显式列出**这五格
  rows: desktopRows(),          // ['系统','就绪'] / ['序列', hasSave ? '有存档' : '未载入']
  escLabel: '关闭', actions: []
});
```

- `modules` 必须显式列（不能用 `null` = "所有已注册的都上来"，否则设置那四页会摊在桌面上）。
- 「继续游戏」那一格带 `available: hasSave`，而 `hasSave` 是 C# 随 `menu.show` 下发的
  （`WebSceneFlow` 读 `StorySaveStore.HasSave`）—— 网页不自己猜有没有存档。
- 点「开始游戏」/「继续游戏」都先 `MainMenuView.hide()` 再发消息：换场景要等 C# 走完，
  中间那段空白不该还压着一个菜单。
- 章节跳跃（在「章节选择」里点一段）走 `Animus.handlers.chapter` → **`menu.chapter`**，
  payload 只有一个 `stepId`。
- **光标指着哪一格**走 `Animus.handlers.hover`（参数是模块 id；不指着任何一格时是 `null`）。
  主菜单页拿它切右侧立绘的表情（`boot.js` 的 `EXPRESSIONS`）；游戏页不接
  （那一页没有网页立绘，`pushHover` 里判了有没有调用方，不接就什么都不做）。
  触发点一共四个：划过瓦片 / `↑↓` / **指针离开导轨** / 关闭界面。
  **"点进某一格"不发**（原来发，见下面那段"进子页不换表情"—— 那条 null
  会把她的脸打回默认）；**开场就位那一次也不发** ——
  菜单一打开她就先换一次表情会很莫名其妙。
  **去重放在出口那一层（`pushHover`），不能拿 `highlightIndex` 代替**：
  开场那一格本来就带着高亮，用 highlightIndex 当依据的话
  「鼠标第一次划到最上面那一格」永远不发，看着就是"高亮着却没换表情"。
- **子页进出**走 `Animus.handlers.page`：进去给页面 id，**回到桌面给 `null`**。
  `null` 这一半是新加的（原来只有"进去"那一句，出来没有通知）——
  主菜单页拿它换她的表情与姿态，见下面「子页 → 她的表情与姿态」。
  游戏页（`app.js`）只认 `'memory'` / `'chapters'`，`null` 对它是无害的。
- **设置页里"光标停在哪一行"**走 `AnimusSettings.handlers.rowHovered`
  （进去给 `row.key`，离开整块列表给 `null`）—— 那是设置模块自己的一对通知，
  和外壳那对是两层不同的"指着"：外壳指桌面瓦片，它指页面里的控件。

> **代价：暖色标题画面（`menu-view.js` 那列选项 + `background.js` 那条索引绳背景）
> 现在不显示了。** 代码都留着，主题要重做时可以直接接回来 ——
> `boot.js` 里去掉 `MainMenuView.hide()` 和 `bg('stop')` 就回到原来的样子。
> 背景的 rAF 也一起停了：看不见的东西不该继续烧 CPU。
> 注意 `boot.js` 里**只有 `bg('stop')`、没有 `bg('start')`** —— 接回来的时候要自己补一个。
>
> 还有一件必须记住的事：`MainMenuView.init()` 仍然要调（`boot.js` 里是 `hide()` 的上一句）——
> 它负责缓存 DOM 和绑事件，不调的话 `hide()` 会撞上空引用直接抛，
> 而抛在 `init()` 中途等于后面所有事都不做（页面看起来什么都没发生）。

#### 「悬停瓦片 → 她换表情」在那次改版里被弄断了（已修）

**症状**：右侧立绘的表情永远是默认那个，悬停哪一格都不变，**也不报错、不警告**。

**原因**：全工程唯一调 `MenuCharacter.setExpression()` 的地方是
`MainMenuView.handlers.hover`（`boot.js`），而它的来源是 `menu-view.js` 绑在
`#menu-buttons` 上的 `mouseover`。可是同一个 `init()` 里已经
`MainMenuView.hide()` —— `#menu-layer.hidden` 是
`visibility: hidden; pointer-events: none`（`menu.css`），**那 4 个按钮永远不会被指到**。
标题画面被 Animus 桌面取代的那一刻，这条回调就变成了死代码，
而 `setExpression` 又没有任何"我没被调用"的迹象（`live2d.js` 只在**调用了但失败**时打日志）。

**修法**：把出口搬到外壳上 —— `Animus.handlers.hover(id | null)`，
`boot.js` 里映射到 `EXPRESSIONS` 再调 `MenuCharacter`。两个界面各归各位：
外壳知道"光标在第几格"，但不知道表情这回事；`boot.js` 知道映射表，但不知道瓦片在哪。

> **教训（和 `Esc` 那一段是同一个）：一个功能只要它的"触发源"和"实现"分在两个文件里，
> 换掉其中一个就得把另一个也过一遍。** 这次换掉的是触发源（标题画面 → 桌面），
> 而实现那一头没有任何编译期或运行期的提醒 —— 前端没有"这个回调没人用了"的检查。
> 映射表原来那句「这张表是按名字猜的」之所以一直消不掉，也是同一个原因：
> 没有触发源就核对不了。**现在可以逐个悬停核对了** ——
> 控制台会打 `[VN:live2d] 表情 → …（走 model.expression）`，对着看就行。
> （表本身已经定下来了，见「已知问题」里那一条。）

**顺带修掉一个真会咬人的缺陷**：`click` / `mousemove` 的 `addEventListener`
原来写在 `buildRail()` 里，而 `buildRail()` 每次"换一摞瓦片"都会跑
（`open` / 进子桌面 / 返回 / `refreshNav`）—— **监听器每换一次就多一份**：

- 点一次带 `children` 的「设置」会被 N 个监听器各处理一遍 → 子桌面被压 N 次栈
  → 退出来要按 N 次「返回」；
- 划过一格会连着换 N 次表情、重画 N 遍预览面板。

`boot.js` 每次收到 `menu.show` 都会调一次 `Animus.refreshNav()`（它里面也调 `buildRail()`），
所以玩家还没动手就已经攒了第二份 —— 这不是理论问题。
现在三个监听器（点 / 划过 / 离开）统一在 `build()` 里注册一次：
`build()` 有 `if (el.root) return;` 兜着，一个页面只会绑一遍。
委托本来也不需要跟着节点重建 —— 它挂在 `el.rail` 上，节点只是它的子元素。

#### 子页 → 她的表情与姿态（`PAGE_MOODS` / `ROW_MOODS`）

「设置」进去之后是四页，**每一页她换个站法**；再细一层，**光标停在哪一行上，
她就对那一项做反应**。两层表都在 `boot.js`：

```js
行（ROW_MOODS） > 子页（PAGE_MOODS） > 默认
```

**第一层：子页**（这一页的底子）

| 子页 | 表情 | 姿态 | 意图 |
|---|---|---|---|
| 章节选择（`memory`） | `死鱼眼` | — | 和桌面那格对齐：悬停什么表情，进去就还是什么 |
| 声音（调音台） | **（不写）** | `dx 80 / dy 16 / scale 1.03 / rotate -1.8` | 往前凑（放大 + 往左倾），但不压到右边的参数 |
| 文字（打字机） | **（不写）** | **`exit: true`（退场）** | 整屏留给那一行字，她不抢戏 |
| 显示（输出） | **（不写）** | **`keepVisible 0.67` / `dy 20`** | 右移到只露半张脸：机器自己的参数，她让开 |
| 立绘 | **（不写）** | **留空（中性）** + `fullBody: true` | 整个人在画面里，正对着你 |

> **「设置」那四页故意不写 `expression` —— 进子页不换表情。**
> 玩家点进来是为了调参数，不是看她变脸；而且那一瞬间她本来正挂着
> "刚划过的那一格"的脸（设置子桌面四格统一发光循环）。
> 这四页只声明**姿态 / 退场 / 取景**。
>
> ⚠ 这里必须把三态分清（`boot.js` 的 `moodNow` 返回值）：
>
> | 值 | 意思 |
> |---|---|
> | 表情名字符串 | 就用这个表情 |
> | `null` | **回默认表情**（桌面：不指着任何一格时） |
> | `undefined` | **没意见，不碰**（进子页时就是这样） |
>
> 混成同一个值的话，"进入子页"会被当成"回默认表情"，她的脸会跳一下。

> **同一个毛病还有第二个来源（更隐蔽）：外壳在"进去"那一刻会先发一条
> `hover(null)`**（"光标不再指着桌面上那一格"）—— 那条也会把她的脸打回默认，
> 而紧接着的 `page(id)` 是"没意见"，接不回来。
> 所以 `animus.js` 的 `enterFolder` **不再发那条 null**：进任何一格都不动她。
> 代价是悬停去重的状态会留在"当初点进去的那一格"上，因此在
> **`leaveFolder`（回桌面）和 `open()` 里把去重状态静默清掉** ——
> 不清的话，指针还停在那一格上，在上面动鼠标不会重新触发，
> 她会一直停在默认表情，要移到别的格子上才恢复。
>
> 真正"指针离开导轨"和"关掉界面"那两种 null 仍然保留（桌面那套没变）。

> **内容列右缘 = 62vw，是一条要记住的线**（`animus.css` 的 `.ax-body`：
> `left: 27vw` + `width: 35vw`）。她**基准位**的左缘在 0.64W（64vw），
> 所以本来就留着 2vw 的余量 —— 但姿态一叠就可能吃掉它：
>
> - `scale > 1` 会把她往左拉（原点在 `82%/100%`，放大是向外扩）；
> - **`rotate` 最吃余量**：倾斜是绕她脚下那条轴转的，
>   画面顶部那一圈会横摆 `≈ 高度 × sin(角度)` —— 1.8° 就是约 60px。
>
> 声音页第一版写了 `dx -44`，两个效果叠起来把她的头发送进了参数列约 30px。
> 现在 `dx +80` —— 左上角落在 **64.5vw**：离内容列 49px 余量，
> 而且正好回到"她基准位那条 0.64W 线"上（放大和倾斜造成的左移被 dx 抵掉了，
> 剩下的只是"变大 + 偏头"）。
> **这两个数要一起动**：`rotate -1.2` 时 `dx` 只要 `+60` 就够（余量一样）。

**`keepVisible`（只露出多少，0~1）** 是"显示"页那一档用的：它按**实测**
换算成横移 —— 量出她现在露在外面多宽，再把 `(1 - keepVisible)` 推出去。
用比例而不是像素的原因和 `TUNING` 一样：像素得先知道她此刻有多宽，而那个宽度只能量。

**0.67 这个数是反推出来的，不是试出来的**（第一版填 0.5，结果把她的脸整个切掉了）：

```
她的左缘   0.64W（animus.css 那条实测）        = 1229px
她的脸     约 0.88W（live2d.js 里 TUNING 实测） = 1690px
可见宽度   1920 - 1229                        =  691px
要让屏幕右缘切在脸中间 → 位移 1920 - 1690      =  230px
→ 留下 (691 - 230) / 691                      ≈ 0.67
```

> ⚠ 0.61~0.67 都可能："她的脸在 0.88W"是在**另一个 position**（`[820,220]`）下量的，
> 而当前是 `[700,120]`，挪了多少只有"一点"这个描述。取 0.67 = 偏保守（宁可多露一点脸）。
> 要更贴脸就往下调。

> 所以**那一档不要再叠 `scale` / `rotate`**：它们会改她的可见宽度，
> `0.67` 就不是"屏幕右缘切在脸中间"这个意思了。
> 行级同样别叠 —— 「全屏」那一行原来试着写了 `keepVisible 0.5`（"再躲远一点"），
> 结果变成"悬停那颗开关她就往右挪"，已经撤掉了（见下面「第二层：行」）。

**`exit: true`（退场）** 是「文字」页那一档用的：整块往**画面下缘**推一个画布高
（距离由画布尺寸算，不是像素常数）。为什么不直接用 `keepVisible: 0`：
往右切看起来是**被画面裁掉**（人还"在"），往下走出去才是**退场**这个动作。

> 她在场外时，那一页**行级的表情反应等于看不见**（文字页的
> `textSpeed` / `autoDelay` 两行只改表情）。要让她在某一行上探头，
> 就在那一行写 `exit: false` + 想要的姿态 —— `moodField` 是逐项接的，
> 行能覆盖页。

> **踩过的坑（记一笔）：`isFinite(null)` 是 `true`。**
> `keepVisible` 第一版在 `live2d.js` 里写成裸 `isFinite(pose.keepVisible)`——
> 而 `boot.js` 对"没写这个字段"的页面返回的正是 `null`，于是它被当成
> `0`（= 一点都不留），横移量变成整个可见宽度，**她被推出屏幕外**。
> 症状是**声音 / 文字 / 立绘三页同时"人不见了"**，而显示页因为写了值看着完全正常 ——
> 看起来像"改动影响了别的页面"，其实是同一个空值在三个页面里各自发作。
> 现在统一走 `numberOr()`（`typeof v === 'number' && isFinite(v)`），
> 和 `app.js` / `animus.js` / `settings-module.js` 里已有的写法一致。
> **`undefined`、空字符串同理** —— 判"有没有给值"要用 `typeof`，不能用 `isFinite`。

这张表**不只装「设置」那四页**：`memory`（章节选择）也在里面，因为它和桌面
那一格必须一致 —— 不写的话，进去那一瞬间她会变回默认表情，看起来像"点坏了"。

立绘页那一档**故意不写 dx/dy/scale/rotate**：取景已经把她铺到画布高度的 94%，
姿态那层再放大就会把头顶和光环裁掉（两层是相乘的：`0.94 × 1.08 > 1`）。
那一页的"上台"由 `fullBody` 本身表达。`fullBody` 这一维见上面
「取景：半身还是全身」。

**第二层：行**（你正指着的那一项，只对设置那四页有效）

| 页 | 行 | 反应 |
|---|---|---|
| 声音 | 主音量 / 音乐音量 / 音效音量 / **语音音量** | `困困眼` / `发光循环`（**语音没被关掉时**）/ `发光循环`（同上）/ **按方向挂着**（见下条规则）+ 再往前凑一点 |
| 文字 | 文字速度 / 自动播放间隔 | `发光循环`（越快越精神）/ `困困眼`（等下一句=发呆）——**她在场外，看不见** |
| 显示 | 主题模式 / 界面主题 / 全屏 | `死鱼眼` / `发光循环`（换光，她亮一下）/ `死鱼眼`（**不动位置**，见下） |
| 立绘 | 显示立绘 / 亮度 / 饱和度 | `空虚眼`（在看自己那个开关）+ 退半步 / `发光循环` / `困困眼` |

四条规则（表里也写着）：

1. **行里只写 `expression` = 姿态沿用这一页的。** 想为某一项换站法就写全
   `dx/dy/scale/rotate`（或 `keepVisible`）—— 那是**绝对值**（替换掉页那一套），不是增量。
   写几项就用几项，**没写的自动从页那张表接上**，所以不会出现"半套姿态"。
2. **没进表的行 = 只沿用页的反应**，不会掉到默认。所以这张表可以只写你有感觉的那几行。
3. **行可以带 `when(settings)` 开关**：条件不成立时**整行作废**（落回下面几层，
   而不是"换成别的表情"）。现在只有音乐/音效那两条用它 ——
   它们要看**语音是不是还开着**：语音关到 0 之后她处在"说不出话"的状态，
   悬停音乐/音效不该把她逗精神。

   写成"整行作废"而不是"再写一遍那时的表情"，是因为**她那时候该是什么样
   只有一个答案**（挂着那一层的空虚眼），在这儿重写一遍就会有两处定义。

4. **"按方向挂着"的反应不在 `ROW_MOODS` 里，在 `VALUE_MOODS`。** 那是**状态**不是悬停反应：

   | 语音音量 | 她 |
   |---|---|
   | 拖到 `0` | `空虚眼` |
   | **往左拖**（调小） | `死鱼眼` |
   | **往右拖**（调大） | `发光循环` |
   | 还没调过（刚进这一页、或者这一趟没碰过它） | **不换表情**（这条规则整个不生效） |

   都是**挂着**的：松手之后她保持那张脸，直到你再次调整、或者离开这一页。

   > **为什么是"方向"而不是"值"。** 第一版按值切区间（`<0.5` 死鱼眼、`≥0.5` 发光循环），
   > 在"从 30% 拖到 60%"这一格上答错了 —— 那是**往大调**，她该精神起来，
   > 而按值算她还在区间左边。玩家要的是"跟着你的动作"，所以记住**最后一次调整的方向**
   > （`voiceTrend`），方向的来源是 `noteVoiceValue()`。
   >
   > 两个必须记住的细节：
   > - **别的设置项变了也会走同一个回调**，所以 `noteVoiceValue` 里"值没变就什么都不做" ——
   >   不然调一次文字速度会把语音的方向也重置掉。
   > - **基线在进/出页面时重新对准**（`Animus.handlers.page` 里 `voiceLast = voiceValue()`）。
   >   开机时 C# 会推一份存档值过来，那**不是**玩家调的；不重新对准的话，
   >   玩家第一次拖滑杆算出来的方向会是反的。
   >
   > ⚠ **这条规则有个"算不算数"的闸门**（`active()`）：只有**这一趟真的调过**
   > （`voiceTrend` 非空）才生效。不加的话，一进「声音」页她就按语音的当前值变脸 ——
   > 那还是"进入子页切换表情"，正是上面那条要避免的。
   > 调过一次之后就挂着，直到离开这一页。

   优先级是**四层**：行（悬停）> 值驱动的基调 > 页 > 默认。
   所以指着「主音量」时她是 `困困眼`，手一移开又回到这一层算出来的那张脸；
   而「语音音量」那一行**只声明姿态**，表情留给 `VALUE_MOODS` ——
   免得同一个"值 → 表情"的关系写两遍（两处写必然漂移）。

   > 这一层也把**触发点**从"鼠标动"扩到了"值变了"：拖一次滑杆会触发几十次重算，
   > 所以 `live2d.js` 里加了**同名表情不重复设**的去重（`appliedExpression`）——
   > 不然后果是控制台刷屏，而且库每收到一次都会重头淡入一遍，看着一直在抖。

> **⚠ 两张表里的位置/大小/倾角都是临时值，还没实测过**（`keepVisible` 除外 ——
> 它是当场量出来的）。`live2d.js` 里 TUNING 那段注释的教训在这儿一样成立 ——
> "这个参数的语义和直觉不一致，只能量"。调的时候不用改文件，控制台直接试：
> `VN.character.setPose({ dx: -24, dy: -6, scale: 1.05, rotate: -1.6 })`
> 或 `VN.character.setPose({ keepVisible: 0.5, dy: 20 })`，
> 试好把数字抄回表里。表情是当场能判断的，姿态要试几轮。
>
> **`keepVisible` 和 `scale` / `rotate` 别一起写**：后两个会改她的可见宽度，
> `0.5` 就不再是"一半"。
>
> **倾斜（rotate）故意只做 1~2 度**：再多就不像"身体语言"，像画面没对齐。
> 行级只有**两处**动了姿态（显示立绘 / 音乐音量），其余都是**只换表情** ——
> 这一层动多了会很吵，玩家的鼠标在设置页里一直在动。

> **「全屏」原来也动了姿态（`keepVisible 0.5` = 再躲远一点），已经撤掉。**
> 症状是"鼠标一放到那颗开关上她就往右挪，像界面在抖"：开关就在行里，
> 悬停它等于进了这一行，而行级焦点一变就会重算姿态。
> 而且那一页她本来就已经躲在 0.67（半张脸）上了，"再躲远"多出来的位移没有信息量。
> **判据**：要让她"在某一项上换个站法"，先问这件事**够不够重** ——
> 够重就该是"换一页"的量级，不是"悬停一行"。
> 开关类的那几行尤其要注意：**开关本身就在行内**，悬停和点击都会触发。

**悬停的表情和子页的表情现在是完全解耦的两件事。**

- **悬停**（`EXPRESSIONS`，九格全在里面）：设置子桌面那四格**统一发光循环**。
- **进去之后**（`PAGE_MOODS` / `ROW_MOODS` / `VALUE_MOODS`）：每一页各有各的状态。

> 它们**曾经是同一张表**：`expressionOf()` 先查 `EXPRESSIONS`，查不到就落到
> `PAGE_MOODS[key].expression`，于是悬停「立绘」预览的就是进去之后那张脸 ——
> 本意是"这一页会让她怎么样"的预告。
>
> **那个预告后来不成立了**：进去之后她的状态变成了"按语音的值和调整方向变 /
> 退场 / 只露半张脸 / 切全身取景"，悬停预告不了，只会让人以为"进去就是那样"。
> 所以四格统一给最有精神的那张，`expressionOf()` 也退回成"只看一张表"：
> **悬停是"我在看这一格"的反馈，不是对下一页的承诺。**
>
> 顺带的好处：这两件事以后各改各的，不会再互相牵连。

> **踩过的坑：`model.expression(undefined)` 清不掉表情。**
> "恢复默认表情"（指针离开导轨、关掉界面）原来走的是
> `model.expression(undefined)` —— 它**不报错，但什么都不做**：库那边按名字/索引
> 找不到定义就直接返回 false。症状是**划过「退出游戏」（空虚眼）之后把鼠标移开，
> 她还挂着空虚眼** —— 清不掉就一直带着。
> 更糟的是它被记成了"已应用"（`appliedExpression`），之后连重试都不会有。
>
> 正确做法是 **`ExpressionManager.resetExpression()`**（`live2d.js` 的 `resetExpression()`，
> bundle 里确实有这个方法）。拿不到它时走退路并**打一条明确的警告** ——
> 那条警告是"恢复默认失效"唯一的线索，不然只能看到"她从上一页带着表情回来"。

姿态走的是**和亮度 / 饱和度完全一样的路**（`settings-module.js` 里有一段解释）：

```
JS 只改 :root 上的 --vn-portrait-dx / -dy / -scale / -rotate
menu.css 里 #oml2d-canvas 那条规则真正生效
```

`keepVisible` **不新增变量**：它在 JS 里就换算成 `--vn-portrait-dx` 了
（量出可见宽度，把 `(1 - keepVisible)` 推出去）。所以 CSS 那一层只认那四个。

三个关键选择，都在 `menu.css` 里有注释：

- **挂在 `#oml2d-canvas` 上，不是 `#oml2d-stage` 上。** stage 的 transform 归库
  （`@keyframes oml2d-stage-slide-in/out` 动的就是它），写上去会和滑入滑出互相覆盖；
  canvas 是它的子元素，动它是**叠加**关系。
- **要 `!important`。** 库那张样式表是运行时 append 到 head 的，文档顺序排在我们的
  `<link>` 后面 —— 同特异度下**它会赢，而且赢得很安静**。
- **`transform-origin: 82% 100%`**，不是右下角。这个数是**推**出来的：`animus.css`
  有一条实测"立绘从 0.64W 就开始"，她在画布上占 0.64W~1.0W，轴心就是 0.82W。
  只有绕她自己那条轴转，`rotate` 才是"倾斜"；绕右下角转是在绕一个一米外的点画弧，
  看着是整体位移。判据：**原地放大、原地倾斜**。

**进出成对由外壳保证**：`animus.js` 的 `notifyPage(id | null)` 在「进子页」和
「回桌面」各发一次（就是 `handlers.page`）。原来只有"进去"那一句，于是任何
"进去时改了什么、出来要改回去"的东西都会卡在里面那套状态上 ——
进了「立绘」页再退回来，她还站在台上放大着。

**行焦点由设置模块发**：`AnimusSettings.handlers.rowHovered(key | null)` ——
和 `handlers.changed`（值变了）分开，因为语义不同（"你看的是哪一项"）。
它**只在用户真的指到某一行时发**（mouseenter / focusin），不在 `focusRow()`
里发 —— 那个函数建页时也会被调一次，在那儿发就等于"页面一建好她先对第一行
反应一次"。去重状态（`hoveredRowKey`）在每次 `refresh()` 里归零：
不清的话，"退出去再进来、又指向同一行"会被当成没变化而一声不吭，
表现是**偶尔没反应**。

### 章节选择：一条时间线，点哪段从哪段接上

「章节选择」（`memory-module.js`）把整条故事铺成**一只翅膀上的一片片羽毛**：

- **章** = 绳上的段，一共 **25 章**
- **幕** = 章的组，一共 **6 幕**：第一幕 4 章 / 第二幕 6 / 第三幕 6 / 第四幕 3 / 结局分支 A 3 / 结局分支 B 3
- **记忆** = 骑在绳下缘上的方块，一节一节
- 点任意一段 = **从那里接着读**

**分组用的是剧本自己的幕标题，不是从 id 里数出来的数字。**

`story.js` 里**幕标题本身也是一条 `type: "marker"`**：整份 1397 步里有 31 条 marker，
其中 25 条是章（`1-1`、`3-6`、`5A-2`…），另外 6 条是幕
（`第一幕-降临——名为草莓奶油的意外`、`结局分支-A-HE永不落幕的茶会`…）。
两者的区别**在数据里就写着**，不用猜：

- `id` **以数字开头**（`/^[0-9]/`）→ 这是一章
- 不以数字开头 → 它是**幕标题**：记住它当"当前幕名"，之后每一章都继承这个名字

> **上一版是"取 id 开头那个数字当章号"，结果错得很显眼。**
> 那样 31 条 marker 会切成 12 组，而且组名会拼成
> 「第 第一幕-降临——名为草莓奶油的意外 章第一幕：降临——名为"草莓奶油"的意外」
> 这种句子 —— **这个 bug 真上过屏**。判据得来自数据本身：幕标题是组名，它不是一章。
>
> 同一个错误的第二半：**5A / 5B 不是"同一个第五章"。**
> 剧本里它们是两个**不同的结局分支**，各自带着自己的幕标题（`结局分支 A` / `结局分支 B`）。
> 按首位数字硬凑会把它们并成一个"第 5 章"，读起来像"第五章有两个版本" ——
> 而剧本的原意是"两条结局"。有现成的名字，就别自己算。

跳步本身不由模块执行：它只把 `stepId` 通过 `Animus.handlers.chapter` 交出去，
主菜单发 `menu.chapter`、游戏里发 `story.jump`，C# 侧统一走
「把 stepId 放进 `StorySaveStore.PendingResumeStepId` → 换到 MainRoom →
`GameManager.StartStory()` 取走并 `PlayFrom`」这一条路（和「继续游戏」共用）。

#### 一个状态上的诚实问题：`open`

进度**未知**时（主菜单页没有 app.js，也就没有"读到哪了"）整条绳标成
`open`（可跳转），**不是 `locked`**。画成一整条灰的"未解锁"是误导 ——
它其实每一章都能点。只有真的知道进度（游戏页）才分 done / current / locked。
四个状态在详情面板里的话术是 `已归档` / `读取中` / `未解锁` / `可跳转`（`STATE_TEXT`）。

同理，主菜单页需要 `story.js` 才画得出章节。**那个文件不在时它老实显示
"拿不到章节列表"，而不是画一条假的时间线** —— 现在已经导出好了（1397 步），
所以主菜单页一进去就有 25 章可看。



参考图的桌面把「继续」「放弃记忆」「离开」和那几格内容入口（DNA / 物品 / 数据库）
混在**同一摞瓦片**里 —— 我们这边那三格对应的是「章节选择」和设置那四页。
所以照做：`Animus.register({ …, run: fn })` 注册的就是
一格动作瓦片，`order` 让它们排在最上和最下，中间的才是文件夹。

- 点它 / 回车 → **执行**（不是进入），外壳走 `module.run()`
- 预览面板的提示语会变成「回车 / 点击 **执行**」——
  写错了玩家会以为按下去会开一个新界面

动作分派放在 `enterFolder` 里而不是点击处理里，是为了让键盘回车和鼠标点击
走同一条路 —— 两条路各写一遍迟早有一条漏掉。

### 导航栈：桌面可以套桌面

参考图里不是固定的"两层"，而是**套娃**：

```
桌面 → 物品 → 武器 / 补给品 / 物品 / 服装 → 具体一件
桌面 → 数据库 → 地点 / 人物 / 概念
桌面 → 设置 → 声音 / 文字 / 显示 / 立绘
```

所以外壳里是一个**栈**（`stack`），不是一个固定的层级：

- 模块带 `children` → 进去的是**新的一屏桌面**（换一摞瓦片），
  顶栏 / 导轨 / 预览面板 / 面包屑都还在原位，**不切到第 1 层**
- 栈里存"进去之前那一屏长什么样"，返回时原样恢复 ——
  **包括光标停在原来那一格上**（不还回去的话，"进去看一眼再退出来"每次都会跳回第一项）
- 面包屑是一条路径：`记忆归档 › 设置 › 声音`

> **左下角那行的文案用我们自己的名字，不照搬参考作品的品牌词。**
> 参考图写的是「ANIMUS桌面」，我们照搬过一版 —— 那是别人的品牌名，
> 放在这个甜味的故事里串味。现在用**这一套界面自己的名字**
> （`animus.js` 的 `BREADCRUMB_ROOT` = `记忆归档`），也就是顶栏那个 kicker，
> 同一个界面上两处说法必须一致。
>
> 同一个毛病还清掉了一处：设置页「立绘饱和度」的说明原来写着
> "配冷白的 **Animus** 会很显眼"，现在是"压在冷白的**归档界面**上"。
> **判据：玩家看得见的文案里不该出现 "Animus"** —— 它只该是代码/文档里的
> 内部叫法（DOM id、模块名、注释）。

`leaveFolder()` 因此有三种情况，从里往外：内容页 → 它所属的那屏桌面 →
栈里的上一屏 → 都不是（那就不动，关不关由调用方决定）。

> **顶层要显式列模块，不能用 `modules: null`。** null 的意思是"所有已注册的
> 都上来"，于是声音/文字/显示/立绘会一起摊在桌面上 ——
> 参考图的桌面是「选项」一个入口，不是四条散项。这个坑当场踩过一次。

### 羽毛上的标签：**选中才出现**

这一页默认**一个字的标签都没有**（整页只有线稿），选中一片羽毛才在它的羽尖上
浮出两行：**幕名 + 章节名**。

- **已推到的**：显示章节名。章节名取剧本自己的 `markerTitle`；
  幕名取它的 `act` 在**第一个全角冒号**处切开的前半段 —— 「第一幕」/「结局分支 A」。
  切不开才退回 `第 N 幕`。
- **没推到过的**：幕名照显示，名字那一行是一个 **`?`**，而且**点了不动**。
  参考图里没读到的条目就是灰的、不告诉你是什么 —— 剧透是次要问题，
  主要是"没读到"这件事本身要在画面上看得见。

```html
<g class="ax-wing-label">                ← 整个 <g> 默认 opacity: 0
  <text class="ax-wing-label-act">第一幕</text>              ← 15px / 字距 0.24em / --ax-ink-faint
  <text class="ax-wing-label-name">归还的钟声</text>          ← 23px / 字距 0.08em / --ax-ink
</g>
```

标签只有**一个**元素，选中谁就挪到谁的羽尖上。不是"每片羽毛藏一个标签"——
那样 25 个元素里 24 个永远是空的，而且 25 份字号/对齐规则迟早会有人改漏一份。

> 标签的位置**直接在 viewBox 坐标里算**，不换算屏幕像素。
> 这样 SVG 一缩放标签跟着缩放，换分辨率、换窗口都不用改代码。
> （换算像素那条老路要拿 `getScreenCTM`，还要处理 DPR 和父元素的 overflow。）
> 两个 `<text>` 都描了一圈底色（`paint-order: stroke` + `stroke: var(--ax-bg-mid)`）——
> 标签一定落在羽毛线上，不描的话字和线糊在一起。

**靠右那几片要反过来对齐**（`text-anchor: end`），否则名字会顶出画布；
`x` 另外再夹进 `[12, 962]` 兜底，万一以后有特别长的章节名也不会跑出去。

#### 拿不到章节时要说清是**哪一种**

「章节选择」有四种"空"的原因，**能做的事各不相同**，所以 `missingReason()`
把它们分开写。只有一句"拿不到记忆序列"的话，看到的人无从下手：

| 判据 | 显示 |
|---|---|
| `hostRepliedEmpty` | Unity 回了一张空表（那个场景里没有正在播的剧本）→ 告诉他去导出 story.js |
| 有 `VN_STORY` 但没有幕标记 | 剧本载入了 N 步但一条 marker 都没有 → 剧本数据的问题 |
| 已请求、未超时 | 正在向 Unity 侧请求章节… |
| 已请求、超时 | 请求了但没有回音 |
| 都不是 | story.js 不在 → 给出 Unity 菜单路径 |

> **顺序有讲究**：先看"是不是有人明确回过话"，再看"文件在不在"。
> 反过来的话，Unity 里明明回了空表却会说成"请求没回音"，把人带偏。
>
> 而"空表"本身也要当回事：它和"没回音"是两回事 ——
> `setProgress` 收到空数组时要记下来并重画，不能直接 `return`。

### 记忆序列：**一只半展开的翅膀，每一片羽毛是一章**

这一页原来是 canvas 画的一条"索引绳"。现在改成 SVG 画的**祈愿的天使 + 一只半展开的翅膀**，
因为羽翼是这个剧本的**核心代价**（5A-2 失去羽翼 / 5B-2 归还羽翼）——
该长成翅膀的东西不该长成一条数据结构。

#### 为什么从 canvas 换成 SVG

三个硬理由，缺一个都不值得重写：

| 理由 | canvas | SVG |
|---|---|---|
| **线稿** | 自己描边、自己处理连接处 | 一句 `fill:none; stroke:...` 就是线稿 |
| **25 片羽毛要能 hover 能点** | 自己做命中测试（点到线段的距离，还要考虑旋转和线宽）| 白送；`pointer-events: all` 让"只有描边没有填充"的形状照样能点 |
| **颜色跟主题走** | 拿不到 `var()`，只能读 `--ax-*-rgb` 再拼字符串（那条路上踩过一次大坑）| `stroke: var(--ax-ink)` 直接跟着四套主题走 |

> `pointer-events: all` 那一条**不是可选项**。SVG 里 `fill: none` 的形状默认只有那 1px 的线算命中，
> 25 片羽毛每片都细得像针，不写这一条根本点不中 —— 而且症状是"点了没反应"，很容易怀疑到别处去。

代价是这一页**不能再每帧动**。这是有意的：**祈愿是静止的。** 所以这里没有 rAF，也没有 `leave()` 要停。

#### 交互（规则和上一版不一样）

| | 行为 |
|---|---|
| 默认 | **一个字的标签都没有**，整页只有线稿。`.ax-wing-label` 是 `opacity: 0` |
| 选中（鼠标划过 / 键盘 Tab）| 在那片羽毛的羽尖上浮出两行：**幕名 + 章节名** |
| 剧情**没推到过**的那一章 | 浮出的是幕名 + 一个 `?`，羽毛本身也暗一档，**而且点了不动** |

标签**只有一个**（一个 `<g>` 里两个 `<text>`），选中谁就挪到谁的羽尖上 ——
不是"每片羽毛藏一个标签"，那样 25 个元素里 24 个永远是空的。
它用 `getScreenCTM` 之外的土办法定位：坐标直接在 viewBox 里算，所以缩放、换分辨率都不用改。

> **不能跳的东西就该看起来不能跳。** locked 那一片画得更暗、`cursor: default`、
> 划过去只亮线不加填充（那个填充的意思是"这里可以过去"，对走不到的羽毛说这句话是骗人）。
> 点击拦截写在事件里，`jumpTo()` 里**再拦一次**当双保险 —— 键盘那条路也走同一个函数。

#### 线稿规则

整张图**没有一处 fill**，只有 stroke：

- `fill: none` 是必须的（SVG 默认 fill 是黑的，不写就是一团黑）
- `vector-effect: non-scaling-stroke` 也是必须的 —— 少了它，SVG 按 `meet` 缩下去之后线会细得看不见
- 位置信号色（`--ax-mark`）只用在**选中 / 当前**那一片羽毛上，和别的页面同一条规矩：整屏只有一个"你在这里"

天使本身是手写的 `<path>`，三笔撑起"这是天使"：**光环的环**、**侧面那个小鼻尖和下巴**、
**合十的双手**。少了任何一个都会变成"一个人站在那里"。

> **眼睛是必须的。** 中间试过一版没有眼睛、头又画大了（头高 132，躯干才 325），
> 结果整个头读成兜帽 —— 侧面线稿里"像不像人"几乎全靠发际线 + 眉 + 眼这三笔。

#### 翅膀的几何：**试了六版，前五版都不行**

这一页花在翅膀形状上的时间最多，把结论和弯路都留下：

| 版本 | 做法 | 结果 |
|---|---|---|
| 一 | 每片羽毛各自定角度 + 长度 | 羽尖半径参差、外缘是锯齿 → **一丛草** |
| 二 | 内曲线（根部）+ 外曲线（羽尖）两条贝塞尔推方向 | 外缘光滑了，但两条曲线近似平行 → 方向几乎一样 → **一排栅栏** |
| 三 | 角度显式扇开 90° | 方向对了，但 25 片各自是独立的叶子、中间有缝 → **须刷** |
| 四 | 覆羽 + 飞羽两排 | 密了一点，仍然是"一盘散叶" |
| 五 | 先画翅膀轮廓、再切成 25 片 | 有整体轮廓了，但每片成了**楔形**（根部 25px、尖端 200px 宽）→ "一片叶子里的排线" |
| 六 | 扇形 + `mask`（后一片把前一片裁掉）| mask 是对的，但**一排 25 片**这件事仍然不成立 —— 渲染出来是一丛草 |
| **七** | **三排**：覆羽 / 次级飞羽 / 初级飞羽，每排 8~9 片 | 成了。**大羽毛** |

**这一串版本认下来的那件几何事实，是这一节的要点：**

> 25 片羽毛要每一片都长得像真羽毛（5:1 左右），翅膀的"厚度"就得有
> 25 × 羽宽 ≳ 1700 单位，而整个 viewBox 只有 580 高。**几何上放不下。**
> 所以"25 片各自是一根漂亮的羽毛"这条路是死的 —— 任何"把 25 片排成一排、
> 每片都要好看、又不许打架"的写法都会撞到这堵墙（三版、四版、五版都在撞它）。
>
> 出路不是"把羽毛画细一点"，而是**别让一排承担 25 片**：
> 真翅膀本来就是分排的（覆羽 / 次级飞羽 / 初级飞羽），每排各十几片，
> 后排压住前排的根部。分排之后**每排只有 8~9 片**，间距就够了 ——
> 这才是"大羽毛"能成立的原因（第七版）。
>
> 章节顺序没变：前面的章落在最里面那排（覆羽），越往后越靠外，
> 最后几章是最长的那排飞羽。

#### 羽毛互相压住：`mask`

线稿没有填充，所以"后画的盖住先画的"**不会自动发生** —— 两片羽毛的轮廓会直接交叉。
给它挂一个 `<mask>`（一整块白 − 前面那几片的黑），第 i 片在被压住的那一块
**整个不画**（连轮廓带羽轴），露出来的正好是"从前面那片后面探出来的一截"，
和手绘里一片一片盖上去是一个意思。

> 每片只遮**前面两片**（同排相邻的那片 + 前一排对应的那片）。
> 全遮是 25×25 = 625 条 path，白烧性能，而实际上只有相邻的会重叠。

有了 mask 才敢把羽毛画到 **40~54 半宽**（前面几版只敢画到 10~15 ——
因为一大就交叉，一交叉就成网状）。

#### 只画半身

身体从头顶一直画到画面下缘、**被下缘裁掉**。这是刻意的：
上一版画了立姿全身，于是 580 高的 viewBox 里身体占掉 500，翅膀只剩一条窄带，
再大的羽毛也铺不开。现在人**大了一倍**，翅膀跟着大了一倍。
这一页的主体本来就该是那只翅膀，不是那个人。

七版的两个关键参数：

- **`fanFrom -112` / `fanTo -12`**：扇开 100°。太窄像梳子，太宽就摊平成半圆。
- **`lenFrom 100` / `lenTo 270` / `lenPow 1.45`**：**这一组是"折扇"和"翅膀"的分界。**
  上一版是 168→262（1.6 倍）配均匀扇角，渲染出来是一把**规规矩矩的折扇** ——
  折扇的特征就是"等长、等角、外缘一排均匀的扇骨"。翅膀相反：**内侧短、外侧长得多**，
  外缘是一条偏的弧。2.7 倍配 1.45 次方才一头低一头高。

**相邻两片共用同一条分界线**（第 i 片的右分界 = 第 i+1 片的左分界），
所以只有缝、没有交叉 —— 前三版全都栽在"相邻两片互相穿插"上。

翅膀画在天使**前面还是后面**也有讲究：现在是先 `<g class="ax-feathers">` 再 `<g class="ax-angel">`，
翅膀在背后。反过来会让羽毛压在她脸上。

| `refresh(page)` | 每次进入 | 重量尺寸、重启自己的动画 |

> 只在帧率上体现。



参考图里最要紧的一条：物品页是散开的图标 + 引线标注，服装页是一个人形剪影，
数据库页是一摞斜放的卡片，第五格（AC 那边是 DNA 页）是一条横贯全屏的绳。

|---|---|---|

| 声音 | `mixer` | 四条竖直电平条 —— 仪表，不是控件（**按行动态生成**：加一条音量通道就自动多一条，见 `buildStageBlock`） |
| 文字 | `writer` | 实时打字机：示例台词按当前速度逐字打出来 |

### 页内三段必须用 flex 列排，**招牌部件不能写死 vh**

页盒的高度是 `.ax-body` 给的（`top: 22vh` / `bottom: 15vh` → 1920×1080 下正好 **680px**）。
页里放三段：页首记录条 / 这一页的招牌部件 / 列表+详情。

上一版 `.ax-page` 是 `display: block`，招牌部件各自写死高度
（`.ax-screen` 30vh、`.ax-rack` 24vh……）。两者相加不用很久就会超：

> **「显示」页实测溢出 72px。** 页首 97 + 缝 23 + 屏框 324 + 缝 28 + 列表详情 280 = 752 > 680。
> 表现是**页脚那个「返回」按钮压到底部详情条上、说明文字被切掉一半**
> （`.ax-foot` 是绝对定位的，它不会跟着内容往下走，只会盖上去）。
> 而且这件事**在 1920×1080 之外看不出来** —— 所有值都是 vh，换个分辨率比例又变一次。

改法是把 `.ax-page` 变成 **flex 列**，招牌部件从 `height` 换成 `flex: 1 1 auto` + 一个
`min-height`（`.ax-rack` 14vh / `.ax-writer` 11vh / `.ax-screen` 18vh）：

- 页盒**一定不会溢出**，剩下的高度由招牌部件自己吃掉（`.ax-page-cols` 和 `.ax-page-head`
  是 `flex: 0 0 auto`，它们按内容走）；
- 部件变矮只是"没那么气派"，不会切掉文字 —— 这是对的取舍。

> **一个高度写两遍必然漂移**（页盒一次、部件一次），和 `overscan` 那次是同一个坑。
> 现在页盒是唯一的输入，部件是派生值。**新加一页的时候照这个来：
> `flex: 1 1 auto` + 一个 `min-height`，不要写 `height: XXvh`。**

### 同步率

顶栏右上那个大数字。两条路：

- 调用方给了真实进度（游戏页传 `AnimusMemory.progress()`）→ 开场从 0 **数上去**，
  这一段"同步中"是 Animus 最有辨识度的几秒
- 没给（主菜单页没有剧情）→ 走一条很慢的环境漂移，只为了"这台机器在跑"

下面那条 18 格的**分段条**比连续进度条更像仪表，最后点亮的那一格会发光 ——
让"刚刚同步到这里"看得见。

数字**一直在动**是刻意的：静止的读数是装饰，走动的读数才让人相信它真的在同步什么。

### 切页的动效

1. **扫描线**从上往下扫一次（0.52s）
2. **失同步**：内容位移 + 文字 RGB 双色偏移 + 阶梯式 clip，外加一条横扫的撕裂带
   （0.34s）—— "信号断了一帧"。这一段换页**每次都放**，不只是首次
3. **碎片拼合**：列表和详情错开 70ms 浮上来
4. 亮弧沿绳跑到新节点

> 真实的 RGB 分离要复制一份 DOM，太贵。文字用 `text-shadow` 做红青双色偏移
> 在视觉上就是同一个东西，而且零成本。

### 背景纹理

网格 + **数据流**（14 条往下淌的细线，纯 CSS 动画，没有 canvas）+ 暗角 + 四角直角标。
Glyph 眼用在「记忆序列」每一条的角上：**红 = 还没收到，灰 = 收过了**。

### 「记忆序列」的数据从哪来

两条路，按优先级：

1. **C# 的 `story.progress`** —— Unity 里走这条。游戏页在 bridge 模式下**根本不加载剧本**
   （C# 一步步推），所以进度只能由它算好发过来。网页发 `story.progress.request`，
   `WebSceneFlow.PostProgress()` 把整张表算好（每幕标 done / current / locked）。
2. **页面自己的剧本** —— 浏览器里预览时走这条。standalone 模式下 app.js 载入了剧本，
   直接数里面的 marker 步就能算；主菜单页没有 app.js，走的是 `window.VN_STORY` 本体。
   两条来源在 `fromLocalStory()` 里就是一句话：`VN.state.story || window.VN_STORY`。

**本地这条要自己分"章"和"幕"**：`id` 以数字开头的 marker 是一章，其余的是幕标题
（详见前面「章节选择」那一节）。分错了就会出现"12 个组、组名拼成一句话"那个 bug。

两条都不通就老老实实**说清是哪一种不通**（见下面那张表），不画一条假的时间线。

> 状态判定（哪一幕已归档、哪一幕正在读）在 **C# 那一侧**做，网页只负责画。
> 这是本项目一贯的分工：C# 是权威，JS 是哑视图。

### 和剧本的统一（**已定：归档**）

**这个问题已经定了：隐喻是「归档」，不是 DNA。**

原来那份界面画的是一条双螺旋（AC 的血脉档案），而**我们的剧本里没有那条线** ——
从头到尾没有血缘、没有遗传、没有族谱。所以双螺旋连同它的横档已经**删掉**，
换成**一根索引绳 + 挂在绳上的样本卡**。这不是换个说法，是连形状一起换掉了：
导轨那条、背景那条，现在都是**一根、没有第二条链、没有横档**。

再往后又改了一次：**章节归档那一页从"绳"换成了"翅膀"** ——
因为羽翼是剧本的核心代价（5A-2 失去羽翼 / 5B-2 归还羽翼），
该长成翅膀的东西不该长成一条数据结构。绳只留在导轨和背景那两处（它们是环境，不是内容）。

定下来的依据全部来自剧本自己（不是我编的词）：

| 决定 | 剧本原话 | 出处 |
|---|---|---|
| 隐喻是**归档** | **「皖萱那时正坐在地毯上，整理前几天拍下来的甜点照片，说是要给自己的『调查样本』做归档」** | **4-1 归还的钟声** |
| 绳上挂的是**样本卡** | 同上 —— 她整理的就是一摞"调查样本" | 4-1 |
| 这一页的口气（章节也是"存档"，状态是「已归档 / 读取中」） | 同上 | 4-1 |
| 它**不能**画成宏大的发光结构 | 见下面那段引文 | 4-3 玩家决策前 |
| 她本人的来处（顶栏 kicker、记录号那类文案） | 天界实习 · 意向课题「调查幸福来源」 | 1-2 自报「实习天使，编号 A-013」 |

4-3 里那句是**直接否掉 DNA 那种视觉**的：

> 原来所谓"回忆"，不是电影那样宏大的蒙太奇。
> 它更像食物残留在舌尖上的味道。平时不觉得怎样，真要失去时，
> 才发现原来早就**一层一层渗进身体里**，成了你的一部分。

双螺旋 + 祖先记忆恰恰是"宏大蒙太奇"那一类：它要求你一眼看到一条**铺满屏幕的、
会发光的、有结构的东西**。剧本要的是"一层一层渗进去"的那种细、慢、不显眼 ——
所以这根绳是**一根细的、会荡的绳**，不是发光结构。

时机也对得上：**天界的召回钟声响起的那一刻，她正在地毯上把甜点照片摊开、
给调查样本做归档。** 那个画面本身就是这个界面。

#### 还没做的（这一轮只换了形状，这几条还开着）

上一轮定下来要动的是纹底、配色和一处演出 —— 都不涉及架构，下面这几条现在的状态：

- **纹底：数据网格 → 羽脉。** 羽翼是核心代价（5A-2 失去羽翼 / 5B-2 归还羽翼），
  把背景那层网格换成羽脉才和主题对上。现在还是网格。**这一条还完全没动。**
- **配色：是不是该往"天界"那边走？** 这一条**一半答了**：现在的四套不是凭感觉配的色，
  每一套都落在**剧本里客厅的一种光**上（午后晴 / 傍晚暖光 / 夜小灯 / 雨夜，
  依据与剧本原话见上面「配色」那一节）——「配色必须有出处」这件事已经做到了。
  但**总的问题还开着**：这四套取的都是**她房间里**的颜色（她就站在 0.64W 之后），
  而"归档"是**天界**的动作 —— 要不要另起一套天界自己的光（白、无影、非人），还没定。
  定了就是往 `animus.css` 里加第五块主题变量（见上面「各给自己的那四个变量」那张表，
  先对着四块 diff 一遍变量名）。
- **纹底和配色是两件独立的事。** 「羽脉」那一条和上面这一条互不依赖：
  配色换过一整轮，纹底还是网格 —— 真要动也可以各走各的，别把它们捆成一个决定
  （捆起来的话，一件没定另一件就永远动不了）。
- **白捡的演出：5A-2 之后羽脉消失**，不用一句台词。前提是先有羽脉。

> 上一轮换隐喻就是这么换的，代价已经量过了：**架构一行都没动**
> （`animus.js` 的外壳、模块注册、切页、同步率、失同步动效全部保留），
> 动的只有导轨/背景那条绳的形状、词汇和文案（以及章节页整页的表现）。

### 设置的数据在 C#，不在网页


数据流是一个环：

```
C# settings.apply  ──►  设置页写进自己那份 current 并刷新控件
控件被动            ──►  本地立刻生效（手感要马上有反馈）
                       └─► send('settings.changed')  ──►  C# 钳制 → 落盘 → 回执 settings.apply
```

为什么权威在 C#：

1. **网页是 `file://` 加载的**。各浏览器对 `file://` 的 `localStorage` 处理不一致（有的按目录隔离、有的直接禁用），存档不能赌这个。**`PlayerPrefs` 是唯一可靠的位置。**
2. **有些设置网页根本做不到**：`Screen.fullScreen`、`AudioListener.volume`、`Application.Quit()` 只有 Unity 能做。
3. **设置要跨场景**。玩家在主菜单里改了速度，进游戏后必须仍然生效 —— 而两个场景里的 MonoBehaviour 互不相识。所以持久化放在**静态类** `UiSettingsStore` 里（寿命正好和这一局游戏一致，不需要 `DontDestroyOnLoad` 搬运）。
4. **换后端时存档必须还在**。以后换成原生 Unity UI 菜单，设置不能跟着丢掉。

几个刻意的决定：

- **事件叫 `settings.changed` 而不是 `settings.set`** ——它是"通知 C# 我改了"，不是"命令 C# 去改"。
- **C# 收到后回一条 `settings.apply` 做确认**，不是多余。界面上显示的是"44%"这种二次加工过的值，让 C# 把钳制后的真值发回去，界面才不会算出一套和存档不一致的数。（网页收到 `settings.apply` 只刷新显示、不再回发，所以这个环不会自激。）
- **存的是物理量（毫秒、0..1），不是滑杆刻度（0..100）。** 滑杆只是给人"慢/快"的直觉，`每字 34 毫秒`才是 C# 和 JS 都能直接用的量。
- **网页主动问（`settings.request`），而不是 C# 主动推。** 主动推必须踩准"网页还没加载完 / 桥接还没连上"的时机，而且这时机在两个场景里还不一样；网页自己知道自己什么时候准备好了。

游戏页本身**没有设置界面**，它只是消费者：开机发一条 `settings.request`，拿到的
`textSpeed` 影响打字机出字节奏，`autoDelay` 影响自动播放间隔。暂停菜单里的设置页
是同一个 `AnimusSettings`，改完两处都更新。

### 语音通道与口型（现在只做了一半）

「声音」页现在有**四条**通道：主音量 / 音乐音量 / 音效音量 / **语音音量**。
语音那条是**先把管子接好**，因为口型要靠它：

| 已经做了 | 还没做 |
|---|---|
| 设置项（网页 + C# + 落盘 + payload，六处齐全） | 语音资源本身（剧本里只有【BGM】和音效，没有台词音） |
| `AudioManager` 的第三个 AudioSource（**场景里没接就自己建**，所以不用动 `MainRoom.unity`） | 谁去调它 —— 对话时按行取语音 |
| `PlayVoice(clip)` | 口型：按帧取幅度 → `CharacterManager.SetMouthOpen` |

**口型只跟语音，不跟 BGM / 音效** —— 否则她会跟着背景音乐一直动嘴。

到时候怎么接（两处记着同一件事：`AudioManager.PlayVoice` 的注释、
`settings-module.js` 里那条 ROW 的注释）：

- **驱动信号**：播的时候按帧取 `voiceSource.GetOutputData(...)` 算 RMS，
  平滑一下喂给 `CharacterManager.SetMouthOpen(value)`（它写的是 `ParamMouthOpenY`，
  接口已经在那儿了）；停播时**记得归零**，不然嘴会停在半开。
- **不用改模型**：`2-3.model3.json` 的 `LipSync` 组是**空的**，所以库的自动口型
  （`model.speak()`）对这个模型无效；但参数是齐的（`ParamMouthOpenY`、
  `Param10` 降颌、`Param8` 鼓嘴、`ParamMouthForm` 嘴形），自己推就行。
- **和表情不打架**：四个 `.exp3.json` 只动 `Param122~125`（眼部开关）和
  `Param54`（发光），一个嘴部参数都没碰。
- **网页立绘那份不在剧情里**（剧情时在场的是 Unity 那位），所以口型的主战场是
  Unity 侧；网页侧要跟的话，挂钩方式见「头顶光圈」那段
  （`internalModel.on('beforeModelUpdate', …)` + `core.setParameterValueById`）。

> **往 `UiSettings` 加字段是「七处一起改」**（2026 年加 `voiceVolume` 时数过一遍，
> 第 6 处就是那次漏了、事后才发现的一处）：
>
> | 处 | 文件 | 漏了会怎样 |
> |---|---|---|
> | 1 | `WebUI/animus/settings-module.js` 的 `ROWS` | 界面上没有这一项；而且网页发出去的 payload 里也没它 |
> | 2 | `Assets/Scripts/UI/UiSettings.cs` | 桥接塞过来的 JSON 里那个字段被静默丢掉 |
> | 3 | `Assets/Scripts/UI/UiSettingsStore.cs` | 读盘 / 落盘 / 钳制 / 恢复默认四处都要加，漏一处就"改了不保存" |
> | 4 | **`WebSettingsChannel.ChangedPayload`** | JsonUtility 对缺失的 `float` 给 **0** —— 每次改任何设置都会把它写成 0 |
> | 5 | `AudioManager.cs` | 通道存在但没人用它（设置改了不响） |
> | 6 | **`animus.css` 的 `.ax-rack`**（只有「声音」页要看） | 原来列数写死成 `repeat(3)`，加第四条电平条会掉到第二行 |
> | 7 | 本 README 的字段表 + 协议段 | 下一个人不知道有这项 |
>
> 第 4 处最阴：**只在 C# 加、网页没加**的话，网页每次发的 payload 都缺这个字段，
> 于是它每次都被写成 0（= 静音），而且只有等这个通道真的出声了才看得出来。
> 反方向也不行（见上面那条）：漏一个字段、不报任何错，
> 表现就是"立绘突然不见了"这种查半天查不到的地方。

### 一行 `choice`：值不是数字的那一项

设置表里除了滑杆（`kind: 'range'`）和开关（`kind: 'toggle'`），还有第三种
**`kind: 'choice'`** —— 现在只有一行用它：「界面主题」（`key: 'animusTheme'`，
在「显示」子页，默认 `lamp`，选项 `noon` / `evening` / `lamp` / `rain`，
也就是上面「配色」那一节里的四套客厅的光）。

- **控件是一排分段按钮**（`.ax-choice` / `.ax-choice-item`，规则在 `animus.css`），不是下拉框：
  四个选项一眼看全、点一下就换，而且"当前是哪个"这件事本身看得见。
- **那一行还带一句 `note`，是写给玩家看的**（`settings-module.js`）：说的是"换的是归档系统
  自己那四套配色，对应客厅的四种光……和游戏画面里那个房间主题是两件事" ——
  因为设置页里同时存在两套叫"主题"的东西（这一项，和游戏页按 `T` 切的那三套），不说清就会互相背锅。
- **值是字符串，而且只能取表里列过的那些。** `apply()` 里那一条校验是必须的：

  ```js
  var ok = typeof value === 'string' && row.options.some(function (o) { return o[0] === value; });
  ```

  存档被手改成别的字符串（`"neon"`）时界面不该跟着一起坏 —— 不匹配就**保持原值不动**。
- **它和别的行不一样：选了立刻改变整个界面。** 别的项要经过 C# 才作用到 Unity，
  这一项在 `onControlChanged` 里直接调 `applyAnimusTheme()`：把 `#animus` 上的 `data-theme`
  改成 `noon` / `evening` / `lamp` / `rain`，再调 `Animus.refreshTheme()` 让 canvas 重读那三个通道三元组
  （不重读就是前面那个"画布留在上一套配色里"的坑）。**落盘仍然走 C#**（`PlayerPrefs`），
  所以 `UiSettings` 里也有 `animusTheme` 这个字段，由开机时的 `settings.apply` 送回来。

> **这一个字段必须同时存在于三个地方**，比别的字段更容易漏（它是字符串）：
> `UiSettings.animusTheme`（默认 `"lamp"`）/ `UiSettingsStore`（`PrefKeyAnimusTheme = "wanxuan.animus_theme"`，
> 读回来时不在白名单里的一律退回默认值）/ `WebSettingsChannel.ChangedPayload.animusTheme`。
> 少一处就会表现成"设了主题，重开又变回去了"。

> **白名单是具名的那一个数组。** `UiSettingsStore.AnimusThemes`（`{ "noon", "evening", "lamp", "rain" }`）
> ＋ `IsKnownAnimusTheme()` 去查它，`Clamp()` 认不出就夹回 `defaults.animusTheme`
> —— 加一套主题就只改**这一个数组**，不用在几处 `if` 里各补一段。
> 它和 `settings-module.js` 里 `animusTheme` 那行的 `options` **必须一起改**：
> 两边对不上就表现成"选了主题，重开又变回去"（C# 那边是权威的）。
> 旧存档里存的 `warm` / `cream` / `dusk` 现在会从白名单里漏掉、自动退回 `lamp`
> —— 这是**对的**，那三套已经不存在了；硬留一条映射反而会把"主题换过一轮"这件事藏起来。

> **`formatValue(row)` 必须单独有一支处理 `choice`，这一步踩过。** 它是详情面板和第 0 层
> 预览面板共用的那个格式化函数（列表那一栏是直接取选中那格的文字，两者现在一致）。
> 少了 `choice` 那一支，字符串就会掉进最后那句 `value ? '已开启' : '已关闭'` ——
> 于是「界面主题」在左边列表里是它自己的标签（当时是「暖木」，按现在的表是「夜」）、
> 在右边详情面板里却写成「已开启」，
> **同一个值两种说法，看着像排版错，其实是类型错**。详情面板那边也别再手抄一遍那句三元，
> 直接调 `formatValue(row)`：一个公式写两遍必然漂移，这个仓库里已经栽过好几次了。
> （所以这一支的写法要**跟着选项表走**，别在文案里写死某一套主题的名字 —— 换主题就得回来改的地方越少越好。）

> **「恢复默认」那条路上也得叫一遍 `applyAnimusTheme()`，这一步也踩过。**
> `resetToDefaults()` 原来只调了 `applyPortraitEffects()` —— 于是按一下「恢复默认」
> 会把 `animusTheme` 改回它的默认值（现在是 `lamp`）并报给 C# 存下来（**存档是对的**），
> 可屏幕上的主题一点没变，要重开一次才生效。
> "改了状态但没同步到界面"是最难发现的一类 bug：状态对、存档对，只有画面是旧的。
> 以后往设置表里加项，记得回头看这里一眼。

### 立绘那三项为什么走 CSS 变量

「立绘」子页的显示 / 亮度 / 饱和度，作用在网页里那位身上（`#oml2d-stage`）。

**不写内联样式**：canvas 是 oh-my-live2d 自己插进来的，库在 resize 和换模型时会重写
`element.style`，写在内联上的 `filter` 会被抹掉。改成 JS 只改 `:root` 上的
`--vn-portrait-brightness` / `--vn-portrait-saturation`、真正生效的是 `menu.css` 里那条规则，
库就碰不到它。关掉立绘用 `visibility: hidden` 而不是 `display: none` ——
后者会让库在 resize 时算出 0 尺寸，再打开时能看见她"跳"回来。

### 顶栏读数为什么要 `setStatus`

游戏页的「当前序列」要等 C# 把进度发回来才知道，而那时 Animus 已经开着了。
没有这个方法的话，顶栏会一直停在打开那一刻的值上 —— 那是"看起来对但其实过期"的显示，
最坏的一种。（`setStatus` 只换那几行读数，不动同步率；同步率归 `setSync`。）

### 拍图要先设视口再导航

这一条是给后来改这套界面的人看的，因为**照着图改会改错**。

headless Chrome 的 `--window-size=1920,1080` 会被浏览器边框吃掉一部分，
实际只有 1904×929；而 UWB 里 CEF 的视口是**正好** 1920×1080。
所以截图脚本必须用 CDP 的 `Emulation.setDeviceMetricsOverride` 覆盖。

关键是**顺序**：必须在 `Page.navigate` **之前**设。设在导航之后的话，
页面已经用错误的 `innerHeight` 初始化过了 —— 立绘（OML2D）会按那个错的高度
算尺寸和停靠位置，而它不会因为视口变化重新量。结果就是：
**同一份代码，两张图里她的大小和位置完全不一样**（0.64W vs 0.74W），
而布局的结论（详情面板放不放得下）也跟着错。

`tools/` 里没有这个脚本（它是排查用的临时工具），但改这套界面之前先确认你的
截图方式是对的 —— 否则你看到的是一个不存在的主菜单。

### 一个踩过的坑：Esc 被两个监听抢

调用方的 `keydown` 是在 `animus.js` **之前**注册的（页面脚本先跑），所以同一个 Esc 会
先进调用方、后进 Animus。调用方在处理"Esc 打开暂停菜单"时，会在这次派发中途就把
`isOpen` 变成 true —— 等轮到 Animus 的监听时，它看到的是一个"开着"的界面，于是又关掉。
现象是**"第一次 Esc 能开，之后每次 Esc 开了又立刻关"**（第一次没事，是因为 Animus 的
监听是在第一次 open 里才注册的，按 DOM 规范不会参与正在派发的那个事件）。

修法是调用方在处理完 Esc 后 `preventDefault()`，Animus 看到 `event.defaultPrevented`
就跳过。加第二个监听的人必须知道这一条。

## 主菜单的动态背景（`background.css` / `background.js`）

主菜单页比另外两套界面多一层：一块铺满视口的动态背景。它**不属于菜单、也不属于设置**，
所以单独两个文件，而不是塞进 `menu.css` —— 那会让"背景改了"看上去像"菜单改了"。

### 画的是什么，为什么是这样

参考的是刺客信条 Animus 那类界面的做法：**界面不是浮在背景上的卡片，而是从背景里长出来的。**
落到这个菜单上就是**一条竖着的索引绳**加**四条线索**（每个选项一条），
线索的起点在画面左侧的暗处、沿途 alpha 从 0 渐亮到节点 —— 线不是"从某个坐标开始"的，
它是**渐渐显形**的。绳的上下两端同样淡出到 0，读起来是"结构从画面外延伸进来"。

**让"从背景里长出来"成立的是线索链，不是那条绳。** 线索链这一部分**一个字都没改**：
它才是那句话的实物（节点的 y 是从菜单按钮上量出来的，见下一节）。
绳只是那个空间里的底色 —— 它要改成别的形状，这句话照样成立。

> **绳是一根，没有第二条、也没有横档。** 上一版这里是"双螺旋 + 横档"（两条链加碱基对），
> 那是 AC 的血脉档案隐喻 —— 剧本里没有血缘、没有遗传、没有族谱，照着画会误导人，
> 所以第二条链和 `drawRungs()` 一起删了。`CFG` 里的 `rungEvery` / `rungAlpha` /
> `strandAlphaTeal` 三个键也一起没了；`TEAL` 那个色常量还留着，但**画面上已经没有东西用它**
> （它是 room 主题的 `--accent`，留着是给以后可能需要强调色的地方）。

层次（从后往前，全在 `#menu-bg` 里，z-index 0）：

| 层 | 内容 | 周期 |
|---|---|---|
| `.bg-grid` | 记忆网格，极慢斜向漂移 | 72s 一轮 |
| `.bg-bloom` | 她身后的呼吸光 | 26s 一次明灭 |
| `<canvas>` | 尘埃 / 线索链 / 索引绳 / 涟漪 | 绳 46s 荡一个周期 |
| `.bg-sweep` | 扫描掠光 | 19s 扫过一次 |
| `.bg-vignette` | 暗角 | — |

### 底色搬到了网页里

这一版之前，右边的奶油色其实是 `MainMenu` 场景里相机的 Background Color —— 页面自己只画了
左边那条遮罩。那条路有两个问题：它是**死**的（想在它上面加动效只能"盖"，盖上去就发灰），
而且网页的样子依赖场景配置，丢进 Build 里跑就可能不是这个色。

现在底色由 `background.css` 的 `#menu-bg` 给出（近墨暖黑 → 暖木色），页面自成一体，
`menu.css` / `settings.css` 的两条横向渐变只负责"把文字区压深"，alpha 因此都比上一版低了约三成。
代价：**主菜单页不再透出 Unity 房间**。对主菜单来说这是对的（它本来就是独立场景），
立绘是网页里的（z-index 9997），不受影响。

### 与 DOM 的耦合只有一处

节点的 y 是从 `#menu-buttons button` 的 `getBoundingClientRect()` **量**出来的，不是按公式算的。
这是故意的：只有量真实位置，"界面长在背景上"才成立；按公式算的话菜单一改版两边就错开。
字体加载完、入场动画跑完、窗口 resize 之后都会重量一次（`sync()`）。

### 这里有一条硬规矩：不要写跨帧累加的状态

全篇**没有** `value += (target - value) * dt / k` 这种写法，也没有 `update(dt)` 式的推进。
所有会动的东西都由当前帧的时间 `now` 直接算出来：

- 入场（绳生长 / 线索延伸 / 节点亮起）—— 纯函数，从各自的 `due` 时刻算；
- 悬停高亮 / 让位 —— 记"**变化发生的那一刻**"（`setActive` / `setMode` 里取的
  `performance.now()`），不是记"哪一帧才发现它变了"；
- 尘埃 —— 总位移取模，不逐帧累加。

三条理由，第一条是实测踩出来的：

1. **靠 `dt` 推进的东西会在 dt = 0 时永久卡住。** 同一时刻连着派发两帧时 dt = 0，
   值就再也涨不上去 —— 现象是"绳画出来了，线索和节点一直不出现"，而代码看着完全正常。
2. 和帧率绑定 → 30fps 和 120fps 手感不一样。
3. 过渡起点记成"发现变化的那一帧"的话，事件到下一帧之间的真实时间被丢掉了。
   正常跑没事，但只要某一刻只渲染了一帧，那一次过渡就算出 0。

结果：任意一帧都能独立算对，跳帧、卡顿、只画一帧，画出来都一样。

### 让位

打开设置页时背景会退：主轴从 `0.50W` 挪到 `0.665W`（设置的内容排到约 `0.61W`，
不退就被压在文字底下），线索链淡到 12%、索引绳淡到 70%（线索链只对菜单选项有意义，
绳是环境，留着当背景）。两边共用同一段时间，因为它们是同一件事。
收起来之后 `boot.js` 会在过渡走完再 `sync()` 一次 —— 菜单卡片那时才弹回原尺寸。

> `CFG` 里这两个系数还叫 `settingsChainDim` / `settingsHelixDim`，名字是**历史的** ——
> `Helix` 那个管的是绳（`drawAxis()` 和 `drawStrand()` 都乘它），别按名字去找螺旋。

### 调参

改 `background.js` 顶部的 `CFG`，控制台里 `VN.background.sync()` 立即重量；
`VN.background.debug()` 打印当前几何（视口 / 主轴 x / 每个节点的 y 和进度）。

几个已经量过的值，别用推理：

- `spineX: 0.50` 落在"文字列右缘"（约 `0.42W`）和"她"（约在 `0.72W` 之后）中间那条空档里。
  她要是往左压上来了就加大这个数。
- `filamentEmergeX: 0.235` 在选项文字（约到 `0.18W`）之后。
- `amplitude: 0.048` 是索引绳的横向摆幅，占视口宽 —— 1920 下是左右各 ±92px。
  **旧值 0.026（±50px）。** 它能动的范围被 `spineX` 卡住：
  绳最左会到 `0.50 − amplitude`，而文字列右缘在 `0.42W` —— 所以 `amplitude` 要留在 `0.08` 以下，
  再大就会横穿到选项文字上。
- `turns: 0.62` 是"从顶到底荡几个来回"。**旧值 2.3** —— 和 Animus 那边同一个道理，
  那个数是给双螺旋用的（一根绳拧 2.3 圈就是弹簧）。
- `spinSeconds: 46`：荡一个周期的秒数。它比 Animus 里那两条都慢（导轨与归档绳都是 34s）——
  背景是环境，慢才不抢戏。
- `strandWidth: 0.0023` 是绳的粗细，占视口宽，1920 下是 4.4px；画的时候还有一层
  `Math.max(1.2, …)` 的兜底，所以窗口再小也不会细到看不见。

`prefers-reduced-motion` 时 `background.js` 只画一帧静态的（结构在，但不动），
CSS 那几层则被 `@media` 关掉。

## 两种运行模式（关键设计）

代码里 `state.mode` 有两个值，视图代码完全相同：

- **`standalone`** —— 浏览器里 JS 自己遍历剧本。用于视觉和节奏评审，不需要 Unity。
- **`bridge`** —— 接进 Unity 后，剧本遍历**完全由 C# 的 `StoryManager` 负责**，JS 退化成哑视图：只渲染，只回报玩家事件。

页面上检测到 `window.uwb` / `window.vuplex` / `window.chrome.webview` / `window.unityInstance` 任一存在时，先切到 `bridge` 并等 C# 开口；**但真正的判据是"C# 是否发来过消息"**（`VNBridge.hostSpoken`）。若 3 秒内一条都没有，说明这次并不是由 C# 驱动，就退回 `standalone` 自己播样本，免得画面一片空白看着像坏了。

> 主菜单页不需要这套模式判断 —— 它没有剧情可遍历，永远只等 C# 的 `menu.show` / `settings.apply`。

这样设计的目的：以后无论换成 Vuplex、UnityWebBrowser，还是决定回退到原生 Unity UI，**需要改的只有"谁遍历剧本"这一件事**，表现层不动。

### 桥接协议

实现在共用的 **`bridge.js`**（版本号 `VNBridge.version = 1`，必须与 C# 的
`WebUiBridge.BridgeVersion` 相同）。两个界面都用它，所以协议只有一份。

**C# → JS**（用 `browserClient.ExecuteJs("window.__vnReceive('...')")` 调用）

```
{ v:1, type:'hello' }                     ← 传输层握手，bridge.js 自己消化，不下发给界面
{ v:1, type:'story.load',    payload:{ story:{...} } }        ┐
{ v:1, type:'marker.show',   payload:{ title } }              │
{ v:1, type:'dialogue.show', payload:{ speaker, content, … } }│ 只发往游戏页
{ v:1, type:'choice.show',   payload:{ stepId, choices:[…] } }│
{ v:1, type:'ending.show',   payload:{ title, message } }     │
{ v:1, type:'ui.hide' } / { v:1, type:'ui.show' }             ┘
{ v:1, type:'menu.show',     payload:{ title, subtitle, hasSave } }    ┐ 只发往主菜单页
{ v:1, type:'settings.apply', payload:{ 十一项设置，字段见下 } }           ← 两页都收
{ v:1, type:'story.progress', payload:{ chapters:[{id,title,state}], progress } }  ← 只发往章节选择
```

`settings.apply` 的十一项就是 `UiSettings` 的全部字段，缺一项都不行：

```
textSpeed  autoDelay  volume  bgmVolume  seVolume  voiceVolume  fullscreen
animusTheme  portraitVisible  portraitBrightness  portraitSaturation
```

**JS → C#**（依次尝试 `uwb.ExecuteJsMethod` → `vuplex.postMessage` → `chrome.webview.postMessage` → `unityInstance.SendMessage('WebUiBridge','OnWebMessage',…)`）

```
{ v:1, type:'ready' }                                          ← 游戏页
{ v:1, type:'dialogue.advance',        payload:{ stepId } }    ┐
{ v:1, type:'dialogue.typingComplete', payload:{ stepId } }    │ 游戏页
{ v:1, type:'choice.selected',         payload:{ index, next } }│
{ v:1, type:'ending.restart' }                                 │
{ v:1, type:'ui.menu' }                ← 游戏页请求回主菜单     ┘
{ v:1, type:'menu.start' }                                     ┐
{ v:1, type:'menu.continue' }                                  │
{ v:1, type:'menu.quit' }                                      │ 主菜单页
{ v:1, type:'menu.chapter',            payload:{ stepId } }    │
{ v:1, type:'settings.changed',        payload:{ 同上十一项 } }   ┘
{ v:1, type:'settings.request' }        ← 两页都发（开机问一次当前设置）
{ v:1, type:'story.progress.request' }  ← 两页都发（章节选择要 C# 把整张表算好）
```

> `menu.continue` 和 `menu.chapter` 是**后加的**，`WebSceneFlow` 两侧都接了：
> 前者走存档（没存档时它只打一条 warning 就忽略），后者和游戏页的 `story.jump` 共用
> 一条路（`StorySaveStore.PendingResumeStepId` → 换到 MainRoom → `GameManager.StartStory()`）。
> `menu.show` 多带的 `hasSave` 是给「继续游戏」那格瓦片用的 —— 网页不自己猜有没有存档。

> `settings.apply` 的 payload **必须十一项齐全**。JsonUtility 对缺失的 `float` 字段给的是 0，
> 对缺失的 `string` 给的是 `null`；靠 0 / null 判断"没发"会把文字速度悄悄改成 0 毫秒
> （瞬间出字），或者让主题退回默认，或者让语音音量被写成 0（静音）。代价太大，
> 所以约定必须齐全。

**`dialogue.typingComplete` 是必须处理的回执。** 打字机效果由前端驱动，C# 必须知道文字何时显示完，否则玩家在打字途中点击会丢事件，自动播放的节奏也会踩空。

**`dialogue.typingComplete` 是必须处理的回执。** 打字机效果由前端驱动，C# 必须知道文字何时显示完，否则玩家在打字途中点击会丢事件，自动播放的节奏也会踩空。

### UWB 实测记录（**已跑通，结论在最下面**）

查过官方文档后，有四条必须先知道的事实：

| 事实 | 影响 |
|---|---|
| **不支持 IL2CPP**（要起独立进程，`System.Diagnostics.Process` 在 IL2CPP 下不可用） | 本工程 `scriptingBackend` 只有 `Android: 1`，Standalone 默认 Mono ✅ 不阻塞。但 Windows 版以后想开 IL2CPP 就没这条路了 |
| **只测过 Unity 2021.3.x**，原文 *"Newer Unity versions should work, but are untested"* | 本工程是 **Unity 6000.1.17f1**，新 5 个大版本 —— **最大未知，只能实测** |
| **改窗口尺寸可能崩 Unity**：*"There is a chance that resizing the screen causes UWB to crash Unity, use carefully!"* | 对要发布的 PC 游戏是产品级风险 |
| **唯一的输入处理器叫 `WebBrowserOldInputHandler`**（旧版 Input Manager） | 本工程原本 `activeInputHandler: 1` = 仅新版 Input System，`UnityEngine.Input.*` 会抛异常。**已改成 `2`（Both）** |

另外：`WebBrowserClient.backgroundColor` 的类型是 **`Color32`（带 alpha）**，暗示内部保留每像素 alpha，所以透明**有希望**——但能不能真透出 Live2D，文档没写，必须实测。

#### 实测结论：全部通过 ✅

在 Unity 6000.1.17f1 + UWB 2.2.8 上逐条验过：

| 验证项 | 结果 |
|---|---|
| 渲染到 `Texture2D`（`BGRA32`） | ✅ |
| **每像素透明**（Diagnostic 场景的红色背景从半透明面板后透出） | ✅ |
| `window.uwb` JS 互操作 | ✅ |
| C# → JS（`ExecuteJs("window.__vnReceive(...)")`） | ✅ |
| JS → C#（`uwb.ExecuteJsMethod` 返回 `true`） | ✅ |
| 鼠标移动 / 点击**坐标准确** | ✅ |
| 键盘 | ✅ |
| 全屏铺满 + 隐藏 UWB 自带导航栏 | ✅ |

> **"隐藏导航栏"不等于"铺满"。** UWB 的 `UnityWebBrowser (TMP)` 预制体里，
> `BrowserController` 的 RectTransform 默认就是缩过的：
> `m_SizeDelta: {x:0, y:-20}`（比父物体矮 20px）+ `m_AnchoredPosition: {x:0, y:-32}`（再往下偏 32px），
> 那是给顶部 42px 的 `Navigation` 条留位置用的。**把 `Navigation` 物体设成 inactive 不会改这两个值** ——
> 结果是导航栏没了，但网页仍然缺一条、还偏着。
>
> 要真铺满，必须在场景里的预制体实例上加三条覆盖（`MainRoom.unity` 和 `MainMenu.unity` 都已加）：
>
> | target 在预制体里是什么 | propertyPath | value |
> |---|---|---|
> | `7454210984040730585` = BrowserController 的 RectTransform | `m_SizeDelta.y` | `0` |
> | 同上 | `m_AnchoredPosition.y` | `0` |
> | `7454210984458747695` = 根物体的 Canvas | `m_SortingOrder` | `100`（压在原生 UI 画布之上） |

**所以"用 AI 生成的 HTML 当游戏前端"这件事，零成本方案已经证实可行。** 文档里写的"新品 Untested""resizing may crash Unity"这些风险没有在这次验证中触发，但发布前仍需自己压一遍。

#### 两个为了绕开 UWB 2.2.8 缺陷而存在的胶水脚本

它们**不是业务代码**，UWB 升级到 3.x 后大概率可以删掉：

| 脚本 | 绕开的问题 |
|---|---|
| `Assets/Scripts/UI/WebInputFix.cs` | UWB 自带的输入层有两处硬伤：①`RawImageUwbClientInputHandler` 的坐标取自 `WebBrowserOldInputHandler`（`UnityEngine.Input.mousePosition`），与本工程 EventSystem 用的新 Input System 对不上，实测能把点击算成 `x=-1197`；②`OnPointerEnter` 在 `!IsConnected` 时直接 return 且只触发一次，导致鼠标移动/键盘的协程永远不启动（表现为 `mousemove` 计数恒为 0）。所以它**自己接管**：坐标改取 `PointerEventData.position`（与命中判定同源），移动/键盘改成每帧轮询。接管时会把 UWB 的 `disableMouseInputs` / `disableKeyboardInputs` 都置为 `true`，**不要在没有同时处理上面那个 `OnPointerEnter` 竞态的情况下把它们改回来**。 |
| `WebUiBridge.cs` 里的 `jsMethodManager.jsMethodsEnable = true` | UWB 默认关闭 JS Methods，而 `RegisterJsMethod` 在关闭状态下会抛 `NotEnabledException`。文档没提这件事。 |

**一个踩过的坑，写下来免得重犯**：手工写场景 YAML 时，fileID **绝不能超出 int32 范围**。曾经用 `7710000001`–`7710000004` 手搓了一个 EventSystem，结果 UWB 和 Unity 自己的 UI（连 `⟳` 刷新按钮）**全部点不动**——因为 Unity 自己的 scene ID 都落在 int32 内，超出范围的对象在反序列化时被静默丢弃。正确做法是**从能用的场景里整段照抄** Unity 自己写的对象块。

UWB 的 JS 互操作与本前端已对齐：

- **C# → JS**：`browserClient.ExecuteJs("window.__vnReceive('...')")` ✅ 与设计一致
- **JS → C#**：**不是 SendMessage**。UWB 注入全局 `uwb`，用 `uwb.ExecuteJsMethod('OnWebMessage', jsonString)`；C# 侧需 `browserClient.RegisterJsMethod<string>("OnWebMessage", 处理方法)` 并开启 `jsMethodsEnable`。`app.js` 的 `send()` 已补上这个分支。

> 本前端统一只传一个 JSON 字符串，正好绕开 UWB 的全部约束（方法必须返回 `void`、参数不支持数组、只支持基本类型与自定义对象）。

**顺带修掉的一个设计缺陷**：原来 `state.mode` 靠"页面上有没有 `vuplex`/`chrome.webview`/`unityInstance` 某个全局对象"来猜桥接模式。不同插件注入的全局名各不相同，猜错会让 JS 和 C# **同时遍历剧情、互相打架**。现在改成由"C# 是否发来第一条消息"决定——判据从"猜"变成"事实"。

**`file://` 下的一个坑（已解决）**：CEF 里 `fetch('story.json')` 会被 CORS 拒绝，所以直接 `initialUrl` 指向本地 `index.html` 时拿不到完整剧本，只会跑样本。现在导出格式已改成 `<script>` 可加载的 `story.js`（`window.VN_STORY = {...}`），并把 `fetch('story.json')` 在 `file:` 协议下整条跳过，免得刷一屏红色报错。

两个共通注意点：

1. **体积**：Vuplex 的 Chromium 会给包体加 360MB（可压到 250MB）。
2. **资源位置**：正式接入时要把 HTML/CSS/JS 和字体一起放进 `StreamingAssets`，不能再走 `../Assets/...` 的相对路径。样式里 `@font-face` 指向 `../Assets/.../ChillRoundF.ttf` 只是为了让浏览器预览能用到游戏字体，`file://` 下可能因 CORS 不生效而退回系统字体。

## 已知缺口 / 待定

- **存档已经做了（自动存档），缺的是"清档"**。上一版这里写的是"没有存档，所以「继续游戏」永远是灰的" ——
  **那条已经过期**：现在 `StoryManager.RememberProgress()` 在每条 dialogue / narration / choice 上
  写一次 `StorySaveStore.Save(stepId)` —— 它挂在 `JumpToIndex()` 这个**所有**步骤变化的唯一漏斗上
  （Advance / SelectChoice / JumpToStep / 开场都走它），所以不可能有哪条路径漏存。
  （marker 和 end 两种故意不存：前者马上被下一步覆盖，后者会让「继续游戏」直接重播结局。）
  `GameManager.StartStory()` 开头取走一次性的
  `PendingResumeStepId`，有值就 `PlayFrom`、没有就 `PlayOpening`。
  所以：**回主菜单不再丢进度，「继续游戏」那一格在有存档之后就会出现**
  （`WebSceneFlow` 随 `menu.show` 下发 `hasSave`，`boot.js` 拿它决定出不出那一格），
  而「开始游戏」也不会被旧存档污染（交接值是"取走即清空"的语义）。
  > 剩下的真缺口是**没人调 `StorySaveStore.Clear()`**（全工程搜不到调用点）——
  > 结局播完之后存档点还停在最后一个可见步上，「继续游戏」会从那里接着读而不是从头。
  > 要补就在 `FinishStory()` 和「开始游戏」那条路上各加一次。
- **原生 Unity UI 没有菜单实现**。主菜单目前只有 Web 版。要换成原生 UI，得在场景里摆控件，然后实现一套和 `menu/*.js` 等价的视图；C# 侧不用改 —— 设置的读写、场景流转都由独立的自动挂载组件负责，跟"谁渲染"无关。Animus 那一套同理（它是共享的，不是某一页的）。
- **记忆序列不区分周目**。走分支结局时"另一条分支的那一幕"仍算 `locked`，这是对的（这一周目确实没读到）。以后要做全收集图鉴，得另外记一份跨周目的已读集合。
- **暂停菜单没有真的"暂停"**。VN 里没有基于时间的玩法，所以"暂停"= 停掉自动播放 + 拦住键盘；剧情本身是玩家驱动的一步一步，不按就不会走。以后要是加了限时选项或演出动画，得在这里补 `Time.timeScale`。
- **`Assets/Scripts/Manager/`（单数）已经删掉了**。它是早先一次写错路径留下的空壳
  （文件自己那段注释就写着"删除建议"），里面只有一个纯注释的 `UIManager.cs`。
  删的时候顺手把 `Assembly-CSharp.csproj` 里那条失效的 `<Compile Include=… />` 也去了 ——
  没有它命令行 `dotnet build` 会报 `CS2001 未能找到源文件`。
  那个 csproj 是 Unity 生成的（`.gitignore` 里就有 `*.csproj`），下次聚焦工程会自己重建，
  所以这条改动不用管。**真正在用的是 `Assets/Scripts/Managers/`（复数），别删错。**
- **发布前要藏掉开发用开关**：控制条上的 `主题` / `背景` / `参考层` 和整个 HUD 都只是评审工具，不是给玩家看的。暂停菜单（Animus）是正式界面，不受此影响。
- **文字速度的取值范围三处不一致**：设置页滑杆只能表达 `8..120` 毫秒（`animus/settings-module.js` 的 `SPEED_SLOW_MS`/`SPEED_FAST_MS`），C# 允许 `1..500`（`UiSettingsStore.Clamp`），游戏页按 `8..120` 钳制（`app.js`）。方向是安全的（C# 最宽），但**这三处常量要一起改**。
- **主菜单场景里 UWB 自带的导航栏被隐藏了**。想临时打开（比如改完 HTML 想按 ⟳ 重载而不用重启 Play），在 Hierarchy 里把 WebView 预制体下的 `Navigation` 物体勾上即可。
- **表情映射：主菜单那一套已经定了，剧本那套 `A/B/C` 仍未定**（两件不同的事，别混成一条）：
  1. **主菜单页的立绘（网页 OML2D）**：悬停瓦片会换表情，用的是 `boot.js` 里那张
     **已经定下来的**表（不再"按名字猜"）：

     | 划过哪一格 | 表情 |
     |---|---|
     | 继续游戏 / 开始游戏 | `发光循环` |
     | 章节选择 | `死鱼眼` |
     | 设置 | `困困眼` |
     | 退出游戏 | `空虚眼` |
     | 设置子桌面那四格（声音 / 文字 / 显示 / 立绘） | `发光循环`（四格统一） |

     想核对视觉效果就逐个悬停，控制台会打 `[VN:live2d] 表情 → 发光循环（走 model.expression）`。
     **⚠ 模型里没有叫"空洞眼"的表情** —— "空洞"是**参数**名（`Param122 空洞眼开关`），
     表情叫 `空虚眼`（`expressions/空虚眼.exp3.json`）。写错名字不会报错到你看得出来：
     库找不到那个表情，她就保持原样不动。
     要改映射就在 `EXPRESSIONS` 里补/改一行，**别去改调用处** ——
     没进表的 key 会落到默认表情，这是规则不是漏写。
     另外**进立绘页时她还会切成全身取景**（`PAGE_MOODS.portrait.fullBody`，
      主菜单和别的页都保持半身），光标停在页面里某一行上还会再反应一层
